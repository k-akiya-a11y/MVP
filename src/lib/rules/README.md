# src/lib/rules

顧客別ルールの照合。構造化ルール（プログラムで判定）と文章メモ（AI に渡す）を扱います。ルールは版管理し、上書きしません。
照合は `match.ts`（ルールの現在の版で、状態が「有効」のものだけを渡す）。

## 既存ルールの確認・編集（`/customers/[customerId]/rules`）

保存済みの `journal_rules` の現在の版を一覧し、選んだルールを編集して**新しい版として保存**する範囲です。

| ファイル | 役割 |
| --- | --- |
| `editor-schema.ts` | 入力検証（純粋関数、zod strict）。DB の check 制約と同じ範囲、実在する日付（うるう年含む）、空白だけの条件は null、条件1つ以上、未知の項目は拒否 |
| `editor-load.ts` | 画面用の読込（読取専用）。顧客・ルール・現在の版・有効なマスタ・口座を、顧客で絞って全ページ読む。他の顧客の行が混ざったら失敗。失敗は固定文（`RuleEditorLoadError`） |
| `editor-submit.ts` | 保存のサーバー側処理（`submitRuleVersion`）。`journal_rule_versions` への INSERT だけ |
| `editor-draft.ts` | 画面の入力欄（文字列）と保存の入力の変換（純粋関数） |
| `src/app/customers/[customerId]/rules/` | `page.tsx`（サーバー）、`rule-editor.tsx`（クライアント）、`actions.ts`（サーバーアクション） |

### 保存の動き

- 入力は `customerId` / `ruleId` / `expectedVersion`（編集元の版）+ 編集項目 + 保存する状態。作成者・作成元・版番号・顧客の上書きは入力として受け付けない。
- ログインは `auth.getUser()` で確認し、作成者はその結果（`created_by`）、作成元は常に `staff`、版は `expectedVersion + 1` にサーバーが決める。
- 顧客・親ルール・最新の版を、担当者の権限（RLS）かつ `customer_id` 明示で読み、返った行の顧客も照合する。最新の版が `expectedVersion` と違えば保存しない（同時編集を上書きしない）。
- 「有効」で保存するときだけ、現在の有効なマスタで処理内容を `findMasterProblems` により検証する。「無効」「提案中」は古い科目がマスタになくても保存できる。口座は状態によらず自分の顧客のものだけ。
- 同じ版の同時保存は主キー重複（23505）で片方が拒否され、競合として返す。自動の再試行・再読込はしない。
- 通信の失敗、応答の欠落、戻り値が書いた行と一致しない場合は「結果不明」とし、保存されていないとは言わない。再読込して版を確認してもらう。
- 親（`journal_rules`）への書込、既存の版の更新・削除はしない。

### 範囲外

この画面での新しいルール（親）の作成（下の「候補から新しいルールを作る」が別画面で担う）、過去仕訳の候補の自動変換、文章メモの編集、管理者限定の制限、権限・RLS の変更。

## 候補から新しいルールを作る（`/customers/[customerId]/rules/new`）

過去仕訳の画面（`past-quality`）の「科目が1種類だけ」の候補から、**「提案中」のルール（親＋版1）を1回の操作で**作る範囲です。有効化はここではしません（既存の編集画面で人が行う）。

| ファイル | 役割 |
| --- | --- |
| `candidate-schema.ts` | URL 検索パラメータ（`key` / `direction` / `accountId` / `requestId`）と保存入力の検証（zod strict、純粋関数）、リンクの作成（`URLSearchParams`）、入力欄→保存入力の変換（空欄を 0 にしない） |
| `candidate-load.ts` | 画面の元データ（読取専用）。`loadPastQuality` で最新の過去仕訳を担当者の権限で読み直し、URL の候補と完全一致するものだけ採用。`readAvailableMasters` で科目の有効性と税区分の選択肢を得る |
| `candidate-submit.ts` | 保存（`createRuleFromCandidate`）。入力検証 → `auth.getUser()` → 候補の再照合 → `findMasterProblems` → RPC を1回 |
| `src/app/customers/[customerId]/rules/new/` | `page.tsx`（サーバー、動的）、`new-rule-form.tsx`（クライアント）、`actions.ts`（サーバーアクション） |
| `supabase/migrations/20261023000300_create_rule_from_past_candidate.sql` | RPC `create_rule_from_past_candidate`（SECURITY INVOKER） |

### 動き

- 過去仕訳の画面が、候補ごとに `randomUUID()`（サーバーで毎回生成）の依頼IDを付けたリンクを出す。依頼IDは URL に固定され、新規画面を再読み込みしても変わらない。依頼IDがそのまま新しいルールのID（`journal_rules.id`）になる。
- URL の値はすべて外部入力として検証する。形式が不正なら読込に進まず、入力値を画面に出さない。
- 候補の取引先キー（完全一致）・向き・科目は読取専用の表示。最新の過去仕訳で科目が1種類でなくなった・キーがなくなった・他顧客のものは「保存できない」と表示する。科目が有効なマスタにない場合も理由を示して保存できない。
- 税区分と優先順位は空欄から始まり、人が明示的に入力する（既定値・科目の既定税区分からの推測はしない）。選んだ税区分 0 は本物の値として扱い、空欄とは区別する。
- 条件は取引先キーと向きだけ。金額・口座・摘要・有効期間・補助科目・メモタグ・摘要の雛形は空（画面で「未指定」とその意味を示す）。後から既存の編集画面で新しい版として足せる。
- 入力は strict で、作成者・状態・作成元・版・有効フラグは受け付けない。RPC に渡すのは `p_customer_id / p_rule_id / p_partner_key / p_direction / p_account_item_id / p_tax_code / p_priority` の7つだけ。
- RPC は同じトランザクションで、アクセス権（`can_access_customer`）、同じキー・向きの過去仕訳が1件以上あり**すべて**指定の科目であること、科目・税区分が同じ顧客の有効なマスタにあることを確認してから、親と版1（`proposed` / `past_entries` / 作成者=`auth.uid()`）を入れる。件数の下限は設けない。
- 依頼IDの重複（23505）は競合として扱い、上書きも再試行もしない。DB が拒否したと確かなエラーは「保存していない」、通信失敗・応答の欠落などは「結果不明」（保存されていないとは言わない）。保存済み・結果不明・競合のあとは画面から再送できない。
- 同じ意味の既存ルールは重複として弾かない。保存前に既存ルールの一覧で確認するよう画面で案内する（重複の方針は設計書にないため決めていない）。
- 検証は保存時点のもの。保存後も過去仕訳が変わらないことの証明ではない。
