# 共有開発ルール

この文書は開発・レビュー・リリース判断の継続的な基準です。既存の [共通指示](../AGENTS.md)（[CLAUDE.md](../CLAUDE.md) と同一内容）、[技術設計書](design.md)、[開発依頼書](requirements.md) を補完します。技術仕様を重複して定義せず、矛盾があれば実装前に Ken と整理します。

ここに書かれた基準は、設定済み・実装済み・検証済みを意味しません。日付、対象コミット、検証結果、未解決事項は各 PR・検証記録で管理し、この文書に固定のテスト件数や一時的な状態を埋め込みません。[完成チェックリスト](completion-checklist.md) で段階ごとに判定します。

## 役割と変更の単位

- Claude は実装を担当し、Codex は実装から独立したレビューを担当します。Ken が業務要件、リスクの受容、リリース可否を判断します。AI のレビュー通過はリリース承認ではありません。
- 作業開始前に担当ブランチ・対象ファイル・作業範囲を共有し、同じ箇所を同時編集しません。引継ぎ時は対象コミットと未完了事項を明記します。
- 1 PR は1目的とします。実装前に、目的、対象外、受入条件、データと権限への影響（影響なしの場合もその旨）を PR または作業計画に記載します。
- UI、業務ロジック、認証・認可、DB、外部連携の責務を分けます。共通の入力検証を再利用し、同じ条件を各所に複製しません。目的に不要な全面書換えやリファクタリングを混ぜません。

## 会計処理で守る不変条件

- 顧客（テナント）をまたぐ閲覧・変更・参照を許可しません。画面の表示制御だけでなく、API・DB の境界でも検証します。
- 明細を黙って捨てません。読取失敗、保留、重複候補、除外には理由と追跡可能な記録を残し、元明細と処理結果の件数・金額を照合します。差異は説明できるまで未解決とします。
- 承認は対象業務の権限を持つ本人だけが行えます。呼出元が渡した役割や確認者 ID を信用せず、サーバー・DB 側で確認します。
- 再試行・再取込・並行処理で二重計上しません。同日・同額・同じ摘要でも正当な別取引は残します。類似だけで自動削除せず、重複候補の判断と根拠を記録します。
- 判断・承認・修正・除外の監査履歴は追記専用とし、過去の履歴を変更・削除しません。訂正も新しい記録で元の判断と結び付けます。

## 不具合への対応

1. まず影響を限定します。必要に応じて対象処理やジョブを止め、影響する顧客・期間・明細の範囲を把握します。
2. バージョン／コミット、環境、利用者の役割、秘匿化した入力、再現手順、期待結果と実際の結果、相関 ID（リクエスト・取込・ジョブ等）を記録します。秘密情報や顧客データをそのまま貼りません。
3. 架空データで再現し、修正前に失敗する回帰テストを追加して、失敗を確認します。再現できない場合は未確認の範囲と理由を明記します。
4. 原因に対する最小限の修正を行い、回帰テストと影響範囲を検証し、Codex の独立レビューを受けます。原因と再発防止策を記録します。
5. 既に影響を受けたデータの修復はコード修正と分けます。対象抽出、修復前後の件数・金額照合、バックアップ、承認、監査記録を備えた別作業として Ken の判断を受けます。コード修正だけで既存データが直ったとは扱いません。

## 検証と結果の記録

- 最新コミットに対するレビューと CI の結果を確認します。追加コミットがあれば影響範囲を再レビュー・再検証します。過去の成功結果で代用しません。
- 正常系に加え、権限不足、別顧客参照、不正入力、重複、再試行、途中失敗、監査記録失敗を検証します。テストを緑にするために期待値を弱めたり、重要な検証を外したりしません。
- 結果は「確認済み（証拠付き）」「未確認（理由付き）」「既知の問題（影響・対応付き）」を区別します。CI がない・実行されていない場合は成功とせず未確認とします。
- モックによるテストと実サービスをつないだ検証を区別します。実結合は隔離した検証環境で架空の業務データを使い、実際の認証・権限制御を確認します。

## 環境・DB・復旧

- ステージングと本番は DB、認証情報、接続先、データを分離し、操作前に対象環境を確認します。
- 適用済みのマイグレーションを書き換えず、新しいマイグレーションで変更します。空 DB からの作成と、既存データのある DB からのアップグレードの両方を検証します。
- 手順書では「停止（被害拡大防止）」「アプリのロールバック（旧版への切替）」「DB の復元（バックアップ等からの回復）」を別々に記載します。実行条件、担当、対象、復旧点、再開条件を定めます。
- 検証環境で停止・ロールバック・復元を演習し、旧アプリと DB の互換性、復旧後の件数・金額・履歴、再試行時の重複防止を照合します。バックアップの存在だけで復元可能とは判断しません。
- アプリのロールバックや DB 復元は外部サービスへの書込を取り消しません。外部状態との不一致を別途照合し、必要な補正は人の判断と承認を経た別作業にします。

## 情報管理と外部操作の範囲

- 認証情報をコード、ログ、PR、AI への入力に入れません。顧客データは必要最小限にし、マスク・秘匿化します。本番データを開発・テストに持ち込みません。
- 依存関係の追加・更新時とリリース判断時に脆弱性を評価し、影響、対策、未解決リスクを記録します。
- この文書追加 PR に freee への書込やメール送信は含みません。この文書はそれらの実行を許可するものではありません。既存の Human Approval・メール非送信の原則を維持します。
