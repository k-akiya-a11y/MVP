# 過去仕訳の読込範囲に上限がない: 実装前の期待記録

作成: 2026-11-05（テストを書く前の期待の記録だけ。本番コードは未変更）。実装後にこの節を書き直さない。期待が誤っていた場合は、末尾に日時と理由を追記する。

## 目的

`loadCustomerContext`（`src/lib/proposals/store.ts`）が読む過去仕訳（`past_journal_entries`）を、設計書（`docs/design.md` の過去仕訳の取込・検索、直近24か月）どおり、基準日（`onDate`）を終端とする直近24か月に限る。

現状は下限（`gte("entry_date", shiftYears(onDate, -2))`、`store.ts:181`）だけで上限がない。基準日より後の日付の過去仕訳が混ざると、過去一致率と AI に渡す類似仕訳が、その明細の時点で存在しないはずの情報で計算される。

この段階では**期待の記録と、失敗するはずの回帰テストの追加だけ**を行う。本番コードは変えない。

## 期待する範囲

- 対象は `entry_date` が **`[shiftYears(onDate, -2), onDate]`**（両端を含む）の行だけ。
- 下限より前（古すぎる）の行、`onDate` より後（未来）の行は含めない。
- 1 ページ目以降の**すべてのページ**で、顧客の絞り込み・下限・上限が同じように付く（ページ分割で条件が欠けない）。
- `shiftYears` の丸め（うるう日 → 平年は月末日）は既存のまま。

## 架空の具体例

基準日 `onDate = 2026-11-05` のとき、範囲は `2024-11-05` 〜 `2026-11-05`。

| 過去仕訳（架空） | entry_date | 含める？ | 理由 |
| --- | --- | --- | --- |
| 古すぎる | 2024-11-04 | 含めない | 下限の前日 |
| 下限の日 | 2024-11-05 | 含める | 下限は含む |
| 範囲内 | 2025-06-15 | 含める | |
| 基準日当日 | 2026-11-05 | 含める | 上限は含む |
| 未来 | 2026-11-06 | 含めない | 上限の翌日 |

うるう日の基準日 `2028-02-29` のとき、範囲は `2026-02-28` 〜 `2028-02-29`（`2026-02-27` と `2028-03-01` は含めない）。

別の顧客の行は、日付が範囲内でも含めない（顧客の絞り込みは全ページで維持）。

## 追記1: 基準日（onDate）の意味の訂正

上の「目的」にある「その明細の時点で存在しないはずの情報」「取引日の時点で存在しない」という趣旨の記述は不正確だった。

- `onDate` は**取引日ではなく、ジョブの基準日（実行日＝今日）**である。明細の `txn_date` ではない。
- したがって上限 `entry_date <= onDate` の意味は「ジョブ実行時点でまだ存在しない（未来日付の）仕訳を使わない」であり、「明細の取引時点の情報だけを使う」ではない。過去の取引日の明細でも、実行日までの過去仕訳は使う。
- 上限の根拠は、設計書の「直近24か月」を基準日を終端とする両端付きの範囲として実装すること。未来日付の行（入力ミス・先日付の取込など）で過去一致率と AI への類似仕訳が歪むのを防ぐ。

## 追記3: コードの流れと根拠

- `loadCustomerContext(customerId, onDate)` は過去仕訳を `fetchAll` 経由で読む（`src/lib/proposals/store.ts:176`）。条件は `customer_id` 一致・`entry_date >= shiftYears(onDate, -2)`・今回追加した `entry_date <= onDate`。
- `fetchAll` は `page(rows.length, rows.length + PAGE_SIZE - 1)` で呼ぶ（`src/lib/supabase/fetch-all.ts:16`）。各ページで同じクエリ関数を呼ぶので、条件は全ページに付く。`fetchAll` は変更していない。
- 上の記録では 3 ページ目を `[2000, 2999]` と想定していたが誤り。開始位置は「ページ番号×1000」ではなく、**それまでに集めた行数**である。範囲内 1,100 行なら、1 ページ目 `[0, 999]`、2 ページ目 `[1000, 1999]`（100 行）、集めた行数が 1,100 になるので終端確認の 3 ページ目は `[1100, 2099]`（空）。Codex のレビューで判明し、テストの期待値をこれに訂正した（期待を弱めたのではなく、実装の仕様に合わせた訂正）。
- 呼出元は `src/lib/proposals/` の判定ジョブ。`onDate` に渡す値は変更していない。

## 追記7: 意味の補正

追記1 の補足。未来日付の過去仕訳は**存在し得る**（たとえば先日付の予定仕訳）。それらは「過去仕訳の日付範囲の外」として対象から除くだけで、「存在しない」と断定するものではない。入力ミスだけが対象ではない。
