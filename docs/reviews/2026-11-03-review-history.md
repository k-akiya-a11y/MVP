# 顧客別の人の確認履歴（読取専用）: 実装前の期待記録

作成: 2026-11-03（実装前）。実装後にこの節を書き直さない。期待が誤っていた場合は、末尾に日時と理由を追記する。

## 目的

承認画面の復旧メッセージは「結果が不明なときは確認の履歴を見る」と案内するが、承認・却下済みの明細は一覧から消えるため、確認先がない。顧客ごとに `human_reviews`（承認・修正・保留・却下）の実際の記録を読むだけの画面 `/customers/[customerId]/history` を追加する。承認画面から顧客リンクで辿れるようにする。

## 入力

- URL の顧客ID、任意の `?page=N`（1 始まり。不正・範囲外の値は 1 として扱う）。
- ログイン中の担当者の権限（`createUserClient`、RLS）。`service_role` は使わない。

具体例（架空）: 顧客「テスト商事」に、(a) 2026-10-01 の出金 12,000 円「ACME 文具」を管理者が承認、(b) 同 10-02 の入金を担当者が理由つきで保留、(c) 10-03 の出金を管理者が科目修正、(d) 10-04 の出金を却下、の 4 件の確認がある。

## 予測する出力

- 新しい記録が上の順（`created_at` 降順、同時刻は `id` 降順）で 1 ページ 50 件。次へ／前へのリンクだけ（検索・絞込なし）。
- 各行: 取引日・金額・入出金・摘要、操作（承認／修正して承認／保留／却下）・日時・確認者（名前を読めなければ「担当者」と ID）、理由、確認ID・判断ID・明細ID。
- 承認・修正: 仕訳候補（変更前）と確定内容を並べ、科目・税区分・取引先などを「名前（ID n）」で表示。修正は差分（前→後）も表示。
- 「承認」はこのアプリでの人の確認であり、freee への登録ではない旨を明記する（登録結果はこの画面では読まず、確認もしない）。
- (a)〜(d) の例では 4 行が (d)(c)(b)(a) の順に出る。(a) は候補と確定内容が同じ、(c) は差分つき、(b) は保留理由つき、(d) は理由があれば表示。

## 例外・失敗時の扱い

- 顧客IDが UUID でない、または RLS で顧客が見えない: 何も読まず 404（フェイルクローズ）。
- 読込失敗・形式不正・他の顧客の行の混入: 固定の汎用エラー文のみ（例外の中身・秘密は出さない）。「記録なし」とは別の表示。
- 記録が 0 件（1 ページ目）: 「まだ記録がありません」。2 ページ目以降で 0 件: 「このページに記録はありません」と 1 ページ目へのリンク。
- 関連データ欠落（判断・明細・マスタ名・担当者名）: 「表示できません（ID …）」など明示し、補完・推測しない。
- サーバーの 1 回の応答上限で行が切れても、次のページ有無の判定を誤らない（上限に達しなくなるまで続けて読む）。

## 変更しない範囲

- 認可・RLS・マイグレーション・依存関係・AI／freee の呼出し・`record_human_review`・承認画面の読込（`loadReviewQueue`）と UI ロジック。
- 書込の操作（ボタン・フォーム・Server Action）は追加しない。ログは追記専用のまま、読むだけ。
- 既存の未コミット変更（提案のリース修正、docs 2 件、検証 README ほか）には触れない。
- 共有コードの変更は、承認画面からのリンク 1 行のみ。

# 実装後の記録（追記: 2026-11-04）

上の「実装前の期待記録」は書き換えていない。以下は実装の実際の内容と、検証の到達範囲。

## 画面の目的

人が読むための読取専用の履歴。承認画面から消えた承認・却下済みの明細について、「誰が・いつ・何を・どう判断したか」を後から確認できるようにする。書込・取消・再確認の操作はない。

- 「承認」「修正して承認」は、このアプリ内での人の確認の記録である。freee への書込（登録）ではなく、登録が済んだことも示さない。登録結果はこの画面では読まず、確認もしていない。
- 名前の表示: 仕訳の科目・取引先などは、表示時点の現在のマスタ（`freee_masters`）から名前を引く。記録そのものに残っているのは当時の freee ID だけなので、現在のマスタ名と当時の呼び名が違う場合がある。無効（`available=false`）になったものは「現在は無効」と付記し、名前がない ID は「マスタに名前がありません」と明示する。推測で補わない。

## 実際のデータの流れと条件（コード参照）

1. `src/app/customers/[customerId]/history/page.tsx` の `ReviewHistoryPage` が URL の顧客IDと `?page=` を受ける。`parseHistoryPage`（`src/lib/review/history.ts`）は 1〜`MAX_PAGE`(10000) の整数以外（不正・複数指定・範囲外）を 1 にする。
2. `createUserClient()`（ログイン担当者の権限、RLS）で `loadReviewHistory` を呼ぶ。`service_role` は使わない。
3. `loadReviewHistory`:
   - 顧客IDが UUID でない、または `customers` が RLS で見えない → `null` → ページは `notFound()`（404）。以降の表は読まない。
   - `human_reviews` を `customer_id` 指定、`created_at` 降順→`id` 降順、`range(offset, offset+50)` で 51 件目まで読む（次ページ判定用）。サーバーの 1 回の上限で切れたら、必要件数に届くか空応答になるまで続けて読む。
   - 読んだ確認の `ai_decision_id` から `ai_decisions`、その `bank_transaction_id` から `bank_transactions`、`reviewer_id` から `staff_members`、表示する ID から `freee_masters` を引く（`.in()` は分割して問い合わせる）。顧客を持つ表はすべて `customer_id` で絞り、返った行の `customer_id` も照合する。
   - 他の顧客の行の混入・読込エラー・形式不正・確認IDの重複は例外。ページ側は固定の汎用文だけを表示し、中身は出さない（「記録なし」とは区別）。
   - 判断・明細・マスタ名・担当者名が読めないときは、履歴の行を消さず、その項目だけ欠落として表示する。
4. 承認画面（`src/app/customers/[customerId]/page.tsx`）の「確認の履歴を見る」リンクから辿れる。

## 発見した境界の不具合と修正（2026-11-04）

- 不具合: `MAX_PAGE`=10000 のページで、より古い記録があると `hasNext` が真になり、次へのリンクが `?page=10001` になる。`parseHistoryPage` は範囲外を黙って 1 ページ目にするため、到達できず、利用者は理由なく先頭に戻される。
- 修正（最小）: `loadReviewHistory` で `hasNext = (51件目がある) && page < MAX_PAGE` とし、最終ページでは次へのリンクを作らない。代わりに新しい戻り値 `olderBeyondLimit`（51件目がある && page >= MAX_PAGE）を返し、ページが「これより古い記録がありますが、この画面で表示できるのはここまでです」と明示する。通常のページ送り・前へ・顧客の絞り込みは変更していない。`MAX_PAGE` は `export` に変更した（テスト・案内文で共有）。
- 回帰テスト（追加のみ。**まだ実行していない**）:
  - `tests/unit/review-history-load.test.ts`: `MAX_PAGE` で 51 件を返す応答を模擬し（50 万行は作らない）、`hasNext=false`・`olderBeyondLimit=true`・`range` の offset を確認。ちょうど 50 件なら案内なし、1 つ手前のページは通常どおり次ページあり。
  - `tests/unit/review-history-page.test.ts`: 最終ページで次へのリンクと `page=10001` が出ず、案内文が出ること、通常ページでは案内が出ないこと。既存のヘルパーに `olderBeyondLimit: false` を追加。

## テスト fixture の修正（2026-11-04、境界回帰テストのみ）

- 事象（Codex 報告。この記録の作成者は実行していない）: 焦点テスト 29 件成功・1 件失敗。`review-history-load.test.ts` の「ちょうど 50 件」ケースで、`history.ts:147` の確認ID重複検査が例外を出した。
- 原因: テスト側の fixture（`data` による固定応答）が、続けての `range` 読込にも同じ 50 件を返していた。ローダーは 50 件で止まらず残り 1 件を問い合わせる（応答上限による切れと本当の終端を区別するため）ので、同一の 50 件が重複した。ローダーと重複検査は正しく、変更していない。
- 修正: fake に、絶対位置 `base` から始まる行の窓を持たせる `window` オプションを追加（fake 内だけの機能）。要求された `range` の絶対 offset に応じて窓の該当部分だけを返し、窓の外は空にする。MAX_PAGE のケースをこれに置き換え、51 件のケースでは追加読込がないこと、ちょうど 50 件のケースでは 2 回目の `range` が `[offset+50, offset+50]` で空応答により終わること、1 つ手前のページの `range` を検証する。
- 変更ファイル: `tests/unit/review-history-load.test.ts` と本記録のみ。本番コードは未変更。修正後のテストは未実行（Codex が再実行する）。
