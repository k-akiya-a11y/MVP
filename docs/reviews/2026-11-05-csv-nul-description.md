# 明細 CSV の摘要に NUL（U+0000）があると、読取を通って DB 登録で失敗する: 実装前の期待記録

作成: 2026-11-05（コード・テストを書く前の期待の記録。実装後にこの節を書き直さない。期待が誤っていた場合は末尾に日時と理由を追記する）。この記録の時点では、製品コードは変更しない。

## 目的

`parseStatementCsv` は、金額が0でない行の摘要（description）に NUL（U+0000）が含まれていても、そのまま `rows` に入れる。`importStatementCsv` は `errors` が空なので `importRows` を呼び、PostgreSQL の text 型は NUL を拒否するため、DB 登録の段階で失敗する。原因となる行番号は利用者に返らず、取込記録にも「どの行が読めなかったか」が残らない。NUL は読取の段階で、行番号つきの行のエラーにして、ファイル全体を取り込まない（DB へ渡さない）べきである。

元コードの根拠（読取のみ。Claude は実行していない）:

- `src/lib/statements/csv.ts:45-88`: 文字ごとに読み、NUL を特別扱いしない。NUL は `field` にそのまま入る。
- `src/lib/statements/parse.ts:194`: `cell(r, header.description).trim()`。`trim()` は NUL を空白として扱わないので、先頭・末尾の NUL も残る。
- `src/lib/statements/parse.ts:213-216`: `signed === 0` の行は摘要を見ずに `ignored` にして `continue` する。
- `src/lib/statements/parse.ts:217-226`: 摘要の検査は空欄だけで、NUL は検査していない。
- `src/lib/statements/import.ts:87-107`: `errors` が空なら `importRows` を呼び、`description` をそのまま渡す。
- PostgreSQL の text 型が U+0000 を受け付けないことは一般的な仕様に基づく前提であり、この記録では実 DB で確認していない（Codex が赤のテストで確認するのはパーサと取込のモックまで）。

「明細を黙って捨てない」「元明細と処理結果の件数・金額を照合する」（`docs/development-rules.md`）、および「1行でも読めない行があればファイル全体を取り込まない」（`import.ts` の方針）に沿わせる。

## 期待する動作（修正後）

1. 摘要の列に NUL（U+0000）を1文字でも含む行は、`errors` に入れる。`rows` にも `ignored` にも入れない。位置は問わない（先頭・途中・末尾、NUL だけの摘要を含む）。
2. 銀行形式（出金・入金の分割列）とカード形式（符号付き1列）の両方で同じ。
3. **金額0の行でも同じ。** 摘要に NUL がある行は、金額0の判定（`ignored` への振り分け）より先にエラーにする。元の CSV として DB に渡せない行が、`ignored` として黙って消えてはならない。
4. エラーの行番号は CSV 上の物理行番号（見出し行を1行目として数える）。クオート内の改行で複数行にまたがる行は、その行の開始行（既存の `CsvRow.line` の定義どおり）。
5. 文言（日本語）は `摘要` と `NUL` を含み、どの文字が問題かが分かるものにする（テストは `NUL` の部分一致で確認する）。
6. 値は一切書き換えない。NUL を取り除く・別の文字に置き換える・切り捨てることはしない。エラーにするだけ。
7. 隣り合う正常な行は通常どおり解釈する（NUL のある行が混ざっても、ほかの行の `rows`/`ignored` の対象は変わらない）。`sourceRowCount` は `rows + ignored + errors`（見出しより後の空でない行数）のまま。
8. 取込（`importStatementCsv`）は既存の関門どおり、`errors` が1件でもあれば `importRows` を呼ばず、`recordFailure` を**1回**呼び、行番号つきの理由と `sourceRowCount` を渡す。取込側の変更は不要な想定。
9. 通常の摘要は変えない: 日本語、`$1`・`$&`・`$$` などドル記号の並び、クオート内の改行を含む摘要、タブを含む摘要は、従来どおり `rows` に入り、摘要の文字列は一文字も変わらない。

## エラー

| 入力（銀行・カードとも） | 結果 |
| --- | --- |
| 摘要の先頭に NUL（`\u0000架空店`） | 該当の物理行に `NUL` を含むエラー。`rows`/`ignored` に入れない |
| 摘要の末尾に NUL（`架空店\u0000`） | 同上 |
| 摘要の途中に NUL（`架空\u0000店`） | 同上 |
| 摘要が NUL だけ（`\u0000`） | 同上（`trim()` で消えず、空欄エラーにもならない。NUL のエラーにする） |
| クオート内の改行をまたぐ摘要に NUL | 行の開始の物理行番号のエラー |
| 金額0（カードの `0`、銀行の出金・入金が両方空欄または0）で摘要に NUL | `ignored` ではなくエラー |
| NUL のある行と正常な行が混在 | NUL の行だけエラー。正常な行は `rows` に残る。取込側はファイル全体を失敗にする |

## 架空の具体例

BOM 付き UTF-8 の合成データ。`␀` は U+0000 を表す（実際のテストでは `"\u0000"` を使う）。

銀行（1行目は見出し）:

```
日付,摘要,出金,入金
2026/11/01,架空店A,100,
2026/11/02,␀架空店B,200,
2026/11/03,架空店C␀,,300
2026/11/04,架空店D,400,
```

- 期待: `errors = [{ line: 3, … "NUL" … }, { line: 4, … "NUL" … }]`、`rows` は2行目・5行目、`ignored` は空、`sourceRowCount` 4。取込では `importRows` を呼ばず、`recordFailure` を1回（`sourceRowCount` 4、line 3 と line 4）。

カード（クオート内の改行あり）:

```
利用日,利用店名,利用金額
2026/11/01,架空店A,980
2026/11/02,"架空
店␀B",500
2026/11/03,架空店C,-300
```

- 期待: `errors = [{ line: 3, … "NUL" … }]`（3行目で始まり4行目で終わる行。報告は開始行の3）、`rows` は2行目・5行目、`sourceRowCount` 3。

金額0（`ignored` に落ちてはならない例）:

```
利用日,利用店名,利用金額
2026/11/01,架空店A,980
2026/11/02,架空␀店B,0
```

- 期待: `errors = [{ line: 3, … "NUL" … }]`、`ignored` は空、`rows` は2行目のみ、`sourceRowCount` 2。銀行の出金・入金がともに空欄の行も同じ。

変わらない例:

| 入力（摘要） | 期待 |
| --- | --- |
| `振込 カ）ユイノヤシロ`（通常の日本語） | `rows` に入り、摘要は同一 |
| `$1 $& $$ $'`（ドル記号の並び） | 同上。一文字も変わらない |
| クオート内の改行を含む `"架空\n店"` | 同上。摘要は改行を含んだまま |
| 途中にタブを含む `架空<TAB>店` | 同上。エラーにしない |
| 金額0で NUL のない摘要 | 従来どおり `ignored`（金額が0）。エラーにしない |

## 変更しない範囲

- `csv.ts`（CSV の分割そのもの）、`values.ts`、`formats.ts`、`import.ts`、`gateway.ts`、DB、UI、依存関係。
