## 目的

`submitReview` と `submitDuplicateResolution`（`src/lib/review/submit.ts`）は、RPC が返した `error.message` をそのまま `{ ok: false, error }` に入れる（`submit.ts:51`、`submit.ts:77`）。この文は `reviewAction` / `bulkApproveAction` / `resolveDuplicateAction`（`src/app/customers/[customerId]/actions.ts`）を通って画面（`review-board.tsx:129,155`、`duplicates-panel.tsx:32`）に表示される。

**証拠のある不具合**: 想定外の SQL エラー、通信エラー（HTML 応答本文を含む）が、利用者の画面に内部情報としてそのまま出る。さらに、通信の失敗は「記録されたかどうか分からない」状態なのに、業務上の拒否（`ok:false`）と区別がつかず、まとめて承認では失敗として集計されて次の件へ進んでしまう。

この段階では**テストと期待の記録だけ**を追加する。本番コード・DB・権限・履歴・アクションの意味は変えない。

## 変更しない範囲

- DB（マイグレーション、`record_human_review`、`resolve_suspected_duplicate`、ロール、履歴テーブル）。
- 新しい権限の発明。管理者／担当者の分担は既存のまま。
- `actions.ts` と UI の `catch`（`review-board.tsx:130,158`、`duplicates-panel.tsx:33`）。既存の「結果不明」表示をそのまま使う。
- 入力検証（zod）、RPC の引数、成功時の戻り値。
- 新しい基盤・シェル・実 DB・認証情報・AI は使わない。テストは実関数に RPC のモックを渡す。

## 期待する設計（実装フェーズ向け）

1. **想定外のエラーは、サニタイズした `Error` を投げる**（`ok:false` で返さない）。既存の UI の `catch` が「結果を確認できませんでした。記録済みの可能性があります」と表示する。投げる `Error` のメッセージ・原因・独自プロパティに、元の `message` / `details` / `hint` / 例外の中身を含めない（サーバーログへの出力が必要なら別途検討。ここでは扱わない）。
2. **まとめて承認で想定外のエラーが出たら `bulkApproveAction` 自体が reject**する。それまでに確定した件があり得るので `failures` に混ぜず、以降の件を送らない。UI は既存の `BULK_UNKNOWN_MESSAGE` と選択解除で、同じ選択の再送を防ぐ。
3. **認識できる DB の拒否だけ `ok:false`**。判定は「メッセージ文が完全一致」かつ「SQLSTATE が実在の組と一致」の両方。文面だけ・コードだけの許可にしない。戻す文は固定の安全な文（既知の文そのもの、または固定文）で、`details` / `hint` は載せない。
4. **値を埋め込む動的メッセージ**は、形が DB の出す形のときだけ認識し、値を含まない固定文にする。
   - `この明細はすでに確認済みです（<状態>）` と `この明細は重複の確認待ちではありません（<状態>）`: `<状態>` は `bank_transactions.status` の check 制約にある 8 値のみ（`new, proposed, approved, registered, on_hold, rejected, duplicate_suspected, duplicate`）。それ以外は想定外。
   - `<勘定科目|税区分|取引先|品目|部門|メモタグ> <整数> はマスタにありません`（P0001）: 値を返さない固定文にし、値が違っても同じ文。整数でない値、末尾の余計な文字は想定外。
5. 関数ごとに別の表で判定する（`submitDuplicateResolution` で `仕訳候補が見つかりません` は想定外。逆も同じ）。

## 実装の説明（追記: 2026-11-05。上の実装前の期待は書き直していない）

変更したのは `src/lib/review/submit.ts` と、既存テスト `tests/unit/review-submit.test.ts` の旧モック 1 箇所だけ。マイグレーション、`actions.ts`、UI、入力検証、RPC の引数、成功時の戻り値は変えていない。

### データの流れ

1. 入力検証（zod）は従来どおり。不正なら RPC を呼ばずに `ok:false`（`submit.ts:97` 以降、`submit.ts:128` 以降）。
2. RPC は `callRpc`（`submit.ts:85`）経由で呼ぶ。送信側が例外を投げた場合（通信失敗、Error 以外の throw）は、中身を一切見ずに捨て、固定文の新しい `Error` を投げる（`submit.ts:89`）。`cause` も独自プロパティも付けない。
3. RPC が `error` を返した場合は `knownRefusal`（`submit.ts:75`）で判定する。
   - `message` と `code` がともに文字列で、関数ごとの表（`REVIEW_REFUSALS` `submit.ts:45`、`DUPLICATE_REFUSALS` `submit.ts:59`）の「文面 → SQLSTATE」と**完全一致**したときだけ、その文を `ok:false` で返す。`details` / `hint` は読まない。
   - 一致しなければ `unknownResultError()`（`submit.ts:72`）を投げる（`submit.ts:111`、`submit.ts:141`）。
4. 投げた `Error` は、既存の UI の `catch`（`review-board.tsx:130,158`、`duplicates-panel.tsx:33`）に届く。`bulkApproveAction`（`actions.ts`）には try/catch がなく、ループ中の throw でそのまま reject するので、以降の件は送られない。

### 主要な判定と理由

- 文面と SQLSTATE を**関数ごとに別の表**で照合する（期待 3・5）。文面だけ・コードだけでは通らない。表の組は、記録済みの 2 つのマイグレーションから拾ったもの。`unknown action` などの内部向け文面は表に入れていない。
- 状態付きの 2 つのメッセージは、`BANK_TRANSACTION_STATUSES`（`submit.ts:42` 付近、check 制約の 8 値）から文面を生成して表に入れた。正規表現で状態を取らないので、範囲外・細工された状態は表に当たらず、想定外になる。
- マスタ不存在は `MASTER_MISSING`（`submit.ts:67`）で「6 種別 + 整数 + 固定の語尾」の形に限定し、`P0001` かつ `submitReview` のときだけ認識する。返す文は値を含まない固定文 `MASTER_MISSING_SAFE`（`submit.ts:68`）。`$` は末尾の改行も許さない（JavaScript の仕様）ので、余計な文字は想定外になる。`\d` は ASCII 数字のみ。
- 想定外のエラーを `ok:false` にせず throw にするのは、通信失敗が「記録されたか不明」であり、業務上の拒否と区別すべきだから。まとめて承認の fail-stop もこれで実現する。

### 業務・データ・権限への影響

- DB、権限、履歴、承認の仕組みへの影響なし。管理者／担当者の分担は DB 側の判定のまま。
- 画面に出る文が変わるのは、想定外のエラーのときと、マスタ不存在のとき（値が消えて固定文になる）だけ。既知の拒否の文は従来と同一。

### 既存テストの修正

`tests/unit/review-submit.test.ts` の「DB のエラーをそのまま返す」は、SQLSTATE のないモックを `ok:false` の期待にしていた。実際の DB が返す組に合わせて `code: "P0001"` を付け、モックの型に任意の `code` を足した。期待値（`ok:false` と文面）は変えていない。新しい回帰テストは一切変更していない。

### 限界・未解決

- **テスト・型チェック・lint は未実行**（今回は実行しない指示）。66 件の失敗が解消するかは Codex の再実行で確認する。ここで「緑」とは言えない。
- 表はマイグレーションの現行文面のコピー。DB 側の文面を変えたら、この表も同時に直す必要がある（直し忘れると既知の拒否が「結果不明」に見える。安全側に倒れるが、利用者には分かりにくい）。DB と表を突き合わせる自動テストはない。
