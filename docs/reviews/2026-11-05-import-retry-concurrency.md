# 明細CSV取込の再試行・並行の回帰テスト: 実装前の期待記録

作成: 2026-11-05（テストを書く前）。実装後にこの節を書き直さない。期待が誤っていた場合は、末尾に日時と理由を追記する。

## 目的

`import_bank_statement`（`supabase/migrations/20261023000100_import_batch_identity.sql`）の再試行・並行時の挙動のうち、`tests/db/concurrency.test.ts` が現状証明していない次の 3 つを、実際の 2 つの独立した DB セッションで固定する。

1. 確定済みの取込の応答が呼出し側に届かなかった後の再試行が、明細を増やさないこと。
2. 先の取込がロールバックしたとき、ロックを待っていた同じ内容の取込が 1 回だけ登録されること。
3. 残高のない同一内容の取込が同時に来ても、直列化され、既存の方針どおり「重複の疑い」として残ること（黙って捨てず、通常の新規明細としても増やさない）。

不具合の修正ではなく、**現在の挙動を回帰テストとして固定する**ことだけが目的。

## 入力（すべて架空データ）

テストごとに固有のタグ付き重複キーを使い、使い捨てDB（既存の `beforeAll`）で行う。既存の `begin` / `commit` / `waitUntilBlocked` / `track` / `within` / `withSessions` を再利用し、新しい基盤は作らない。

- 共通: 顧客 `CUSTOMER_A`、口座 `WALLET_A`、`bank_generic`、担当者 `staff` の権限。
- 例 1・2（残高あり、残高は連続）: 10-27 出金 9,020 円 "SAMPLE TELECOM"（残高 90,980）、10-31 入金 330,000 円 "SAMPLE CLIENT"（残高 420,980）。合計 入金 330,000・出金 9,020。
- 例 3（残高なし、`balance: null`）: 出金 1,200 円 "SAMPLE STATIONERY"、入金 5,000 円 "SAMPLE REFUND"。合計 6,200 円。

## 予測する出力

### (1) 応答を失った再試行（模擬）

手順: セッション A で取込を実行して確定し、**返り値を捨てて**接続を閉じる。別の新しいセッション C が同じ内容を再実行する。

- 「応答の消失」は、返り値を使わずに接続を閉じることで**模擬した通信断**である。実際の HTTP・ブラウザ・ネットワーク断の再現ではなく、その証明にもならない。
- 再試行の結果: 登録 0・読み飛ばし 2・重複の疑い 0、読み飛ばし金額 339,020 円、登録金額 0 円。
- 明細は元の 2 件のまま。ID・取込ID・キー・状態・金額が再試行の前後で完全に同じ。再試行の取込IDを持つ明細は 0 件。
- 取込記録は 2 件（元・再試行）。元の記録は再試行の前後で変わらない。2 件は同じ `batch_hash`。各記録で 読めた行 = 登録 + 読み飛ばし + 疑い。
- 金額: 明細の金額合計 339,020 円 = 入金 330,000 + 出金 9,020。

### (2) 先の取込がロールバックし、待っていた同一取込が成功

手順: A が取込を実行して未確定のまま保持。B が同じ内容を実行し、顧客単位の取込ロック（待ち種別 `advisory`）で待つことを観測。A をロールバックし、B を確定する。

- B は登録 2・読み飛ばし 0・重複の疑い 0（先の取込は存在しないので再実行ではない）。
- 明細は B の取込ID の 2 件だけ（状態 `new`）。金額合計 339,020 円 = B の登録金額 = 入金 + 出金。
- A が作りかけた取込ID は `statement_imports` にも `bank_transactions` にも存在しない。この重複キーの取込記録は B の 1 件だけ。

### (3) 残高なしの同一取込が同時に来る

手順: A が取込を未確定のまま保持。B が同じ内容を実行し、`advisory` で待つことを観測。A を確定し、B を確定する。

- 直列化の証拠: B は A の確定まで完了しない（`waitUntilBlocked`）。
- B の結果: 登録 0・読み飛ばし 0・重複の疑い 2、疑い金額 6,200 円。残高がない行は、同じ内容でも読み飛ばさない既存の方針（マイグレーション冒頭のコメントのとおり）。
- 明細は 4 件: 元の 2 件（`new`）と、B の取込IDを持つ 2 件（`duplicate_suspected`、キーは `<元のキー>:suspected:<B の取込ID>`、`duplicate_of_id` が元の明細）。B の取込IDで状態 `new` の明細は 0 件（通常の新規重複ではない）。
- 金額合計 12,400 円（= 元 6,200 + 疑い 6,200）。取込記録 2 件、各記録で 読めた行 = 登録 + 読み飛ばし + 疑い、B の記録は 登録金額 0・読み飛ばし金額 0・疑い金額 6,200。

## 例外・失敗時の扱い

- ロック待ちを観測できない、または待たずに完了した場合は、既存の `waitUntilBlocked` と同じくテストが失敗する（重なりを観測できないテストを成功にしない）。
- 各操作は `within`（15 秒）で打ち切り、セッションは `withSessions` の `finally` で必ず終了する。未確定のトランザクションは接続の終了で取り消される。
- 期待を満たさない場合は、期待値を弱めず、挙動の差として報告する（本番コードは直さない）。

## 変更しない範囲

- 本番コード、マイグレーション、重複判定の方針（残高なしは疑いとして残す、再実行だけ読み飛ばす）、RLS・権限。

- 新しい依存関係・環境変数・CI設定・基盤。外部サービス・AI・認証情報・書込は使わない。
- 既存の未コミット変更。
- 重複の疑いの人による解決、実際の HTTP/ブラウザ/ルートの再試行（本テストの対象外。別途確認が必要）。

## テストごとの内容と理由

1. **応答を失った再試行（模擬）**: `inTx` で取込を確定し、返り値を捨てて接続を `end()` する。元の取込IDは応答ではなく `statement_imports` から読む。新しいセッションが同じ内容を再実行し、明細が前後で完全に同じ（`toEqual`）こと、再試行の取込IDの明細がないこと、元の取込記録が変わらないこと、同じ `batch_hash` を確認する。**模擬した通信断であり、実際の HTTP・ブラウザの再試行ではない。**
2. **ロールバック後の待機側**: A が未確定のまま保持、B が `advisory` で待つことを `waitUntilBlocked` で観測してから A をロールバックする。B が 1 回だけ登録し、A の取込ID が記録にも明細にも残らず、金額が入金 + 出金 = 登録金額になることを確認する。
3. **残高なしの同時取込**: 同じ待機の観測の後、A を確定する。B が読み飛ばさず 2 件を `duplicate_suspected`（キー `…:suspected:<B の取込ID>`、`duplicate_of_id` = 元の明細）として登録し、`new` の明細は元の 2 件のまま、金額合計は元の 2 倍、取込記録の件数・金額の照合が合うことを確認する。既存の方針（残高なしは再実行でも疑いとして残す。マイグレーション `20261023000100`）をそのまま固定するもので、方針は変えていない。
