# 銀行 CSV の出金/入金見出しの片方が認識できないとき、空欄(0円)として読まれる: 実装前の期待記録

作成: 2026-11-05（コード・テストを書く前の期待の記録。実装後にこの節を書き直さない。期待が誤っていた場合は末尾に日時と理由を追記する）。

## 目的

`parseStatementCsv`（`src/lib/statements/parse.ts:146`）は `hasSplitColumns = header.withdrawal >= 0 || header.deposit >= 0` で、出金・入金の**どちらか一方**の見出しが認識できれば分割列として読む。認識できなかった側の列は `cell()` が `""` を返し、`parseYen("") ?? 0` で金額0として扱われる。形式定義 `bank_generic`（`formats.ts:29-40`）は出金・入金の両列を前提にしているのに、片方の見出しが未認識（綴り違い・未対応の別名）でも検出されない。

Claude は実行していない。コード読取による予測:

- 入力 `日付,摘要,出金,未対応入金\n2026/11/01,架空支払,100,\n2026/11/02,架空入金,,500`
  - 「入金」が未認識（withdrawal=2, deposit=-1）。1行目は支出100として成功。
  - 2行目は出金空欄・入金列なし = 金額0 → `ignored`（「金額が0」）。500円の入金が黙って捨てられ、`errors` は空で一部成功する。
- 逆方向 `日付,摘要,未対応出金,入金` では、出金が0円扱いになり、入金だけが取り込まれる。

「明細を黙って捨てない」「元明細と処理結果の件数・金額を照合する」（`docs/development-rules.md`）に反する。

## 期待する動作（修正後）

1. 銀行形式（`withdrawal` と `deposit` の見出し候補を両方持つ形式）で、出金・入金の**片方だけ**見出しが認識できたときは、行を1行も解釈する前に、ファイル全体を失敗にする。
2. 失敗時は `rows: []`、`ignored: []`、`errors` に認識できなかった側 **1件**。行番号は見出しとして選ばれた行の CSV 上の物理行番号（前置き・空行・クオート内改行があっても `csvRows[headerIndex].line`）。`sourceRowCount` は見出し行より後の空でない行数を保持する（`countDataRows`）。
3. 文言（日本語）は、認識できなかった見出しを `「入金」の列が見つかりません` または `「出金」の列が見つかりません` で始め、続けて形式として両方の見出しが必要なことを説明する（テストは前半の部分一致で確認する）。
4. 取込（`importStatementCsv`）は既存どおり `errors` が1件でもあれば `importRows` を呼ばず、`recordFailure` を**1回**呼び、行番号つきの理由と `sourceRowCount` を渡す。
5. 見出しの判定は既存どおり NFKC＋空白除去後（`normalizeHeader`）で、銀行の別名（`お支払金額`・`お預り金額` など）も有効な見出しとして数える。
6. 出金・入金の見出しが**両方ある**ときは従来どおり。列内の個々の空欄（出金だけ・入金だけに値がある行）は許可。両方空欄/0の行は `ignored`（金額0）。残高の見出しは従来どおり任意。
7. 出金・入金の見出しが**両方ない**銀行形式は既存の `金額の列が見つかりません`（見出し行の物理行番号）のまま変えない。
8. カード形式（`signedAmount` のみ、`withdrawal`/`deposit` の候補なし）は変えない。`利用金額` などの符号付き金額で読み、マイナスは返金（入金）。金額見出しがなければ既存どおり `金額の列が見つかりません`。
9. 見出しが曖昧（同じ意味の物理列が複数）の判定は先に行い、既存どおり。この修正はそれを変えない。
10. 単列の銀行形式（符号付き金額1列）の自動推測・新規対応はしない。

## データの流れと主要な分岐

`parseStatementCsv` → `parseCsvWithLines` → `locateHeader`（見出し行と各列の位置） → 曖昧見出し（既存、先に判定） → **今回の検査** → 金額列なし（既存） → 行ごとの解釈。

今回の検査の条件は次の 3 つがすべて成り立つとき。

1. `format.columns.withdrawal` が 1 件以上の候補を持つ。
2. `format.columns.deposit` が 1 件以上の候補を持つ。
3. 見出しで認識できた出金列と入金列のうち、ちょうど片方だけがある（`(withdrawal >= 0) !== (deposit >= 0)`）。

成り立てば `rows: []`、`ignored: []`、`errors` は認識できなかった側 1 件（行番号は `csvRows[headerIndex].line` の物理行番号）、`sourceRowCount` は `countDataRows`。取込側は既存どおり `errors` があれば `importRows` を呼ばず失敗を 1 回記録する。

| 入力 | 結果 |
| --- | --- |
| 出金・入金の両方あり | 従来どおり。両方の金額が 0 相当（両方空欄・0）の行だけ `ignored`。片側だけ非 0 の行は正常な入出金として取り込む。残高は任意 |
| 片方だけ（銀行） | 新しいエラー（「入金」または「出金」の列が見つかりません…） |
| 両方なし（銀行） | 既存の「金額の列が見つかりません」 |
| カード（`signedAmount` のみ） | 条件 1・2 を満たさず、変更なし |

## 設計の選択

「銀行形式だから」ではなく「`format.columns` で出金・入金の両方が定義されている形式」に適用した。将来、出金または入金の片方しか定義しない単列の形式を意図的に足したときに、その形式まで不必要に禁止しないため。今の `bank_generic` は両方を定義しているので対象になる。
