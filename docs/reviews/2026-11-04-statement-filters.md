# 明細一覧の絞り込み（読取専用）: 実装前の期待記録

作成: 2026-11-04（実装前）。実装後にこの節を書き直さない。期待が誤っていた場合は、末尾に日時と理由を追記する。
前提: [顧客別の明細一覧](2026-11-04-statement-ledger.md)（`src/lib/statements/ledger.ts`、`src/app/customers/[customerId]/statements/page.tsx`）。

## 目的

明細が多い顧客で、未判定（new）や取り込んだばかりの明細を、全ページをめくらずに探せるようにする。既存の一覧に、状態・口座・取引日（開始日／終了日）の絞り込みを足す。読取専用のまま。

## 入力

URL のクエリ（GET のフォームだけ。POST・Server Action は使わない）。

| 名前 | 値 | 未指定の扱い |
| --- | --- | --- |
| `status` | 既存 8 状態のどれか、または `all` | 空・`all`・なし = 全状態 |
| `wallet` | UUID（この顧客の口座） | 空・なし = 全口座 |
| `from` | 実在する日付 `YYYY-MM-DD`（その日を含む） | 空・なし = 下限なし |
| `to` | 実在する日付 `YYYY-MM-DD`（その日を含む） | 空・なし = 上限なし |
| `page` | 既存の `parseHistoryPage` のまま | 1 |

具体例（架空）: 顧客「テスト商事」、口座「普通預金」「カード」。
- `?status=new` → 未判定だけ。
- `?status=new&wallet=<普通預金のID>&from=2026-10-01&to=2026-10-31` → 3 条件の AND。10-01 と 10-31 の明細も含む。
- `?from=2024-02-29` は有効（閏日）。`?from=2026-02-29` は無効。

## 予測する出力

- 絞り込みはすべて SQL 側（Supabase の `eq` / `gte` / `lte`）で、`order`・`range` より前に適用する。ページ分を読んでから画面側で絞ることはしない。サーバー側の上限で切れて続けて読む処理（既存）でも、毎回同じ絞り込み・同じ並び・同じ顧客IDで読む。
- 並びは既存のまま（`txn_date` 降順、`id` 降順）。同日・同じ条件の明細の並びは `id` で安定する。
- フォームは GET の 1 つだけ。「絞り込む」（適用。`page` を送らないので 1 ページ目に戻る）と「リセット」（絞り込みなしの一覧へのリンク）の 2 つを明示する。
- 前へ／次へ、範囲外ページの「最初のページに戻る」は、有効な絞り込みをクエリに残す。値は `URLSearchParams` で組み立てる（生の文字列を連結しない）。リセットは絞り込みを全て外す。
- 口座の選択肢は、ログイン中の担当者の権限（`createUserClient`）で `wallets` を `customer_id` で絞って読む。1 回の応答上限で切れても、上限件数（200）まで続けて読み、超えたら「一部のみ表示」と示す。
- 選んだ口座がこの顧客の口座として確認できない（他の顧客の口座・存在しない）場合は、明細を読まず、どちらの場合も同じ固定文を出す。口座名は出さない。条件を広げて読むことはしない。
- 0 件の表示を 3 つに分ける:
  1. 絞り込みなし・1 ページ目: 既存の文（取り込まれていないことの証明ではない）。
  2. 絞り込みあり・1 ページ目: 「条件に合う明細は見つかりませんでした」。この顧客に明細がないという意味ではない、結果不明の取込を「取り込まれていない」とは判断できない、と書く。リセットへの案内。
  3. 2 ページ目以降: 既存の範囲外の案内（絞り込みを残した最初のページへのリンク）。
- 件数表示は「条件に合う明細」と分かる文言にする（絞り込みあり）。

## 例外・失敗時の扱い

- 不正な値は黙って捨てない。次の場合は明細を読まず、固定の安全な案内文を出す（入力値は文に含めない。生のエラーも出さない）:
  - `status` が 8 状態・`all` 以外／`wallet` が UUID でない／`from`・`to` が `YYYY-MM-DD` でない・実在しない日付（例 2026-02-29、2026-13-01、2026-04-31）
  - `from` > `to`（逆順）
  - いずれかの名前が複数回指定された（配列になる）
- 無効な項目があっても、有効な他の項目はフォームに残す。ただし一覧は出さない（条件を落として広い結果を出さない）。
- 顧客が見えない・UUID でない顧客ID: 既存どおり 404。無効な絞り込みでも、顧客が見えない場合は 404 のまま（顧客と口座の選択肢だけは読む）。
- 読込エラー・形式不正・他顧客の混入は既存どおり例外 → 画面は固定の汎用文。加えて、返った行が絞り込み条件に合わない場合も例外にする（防御）。
- 結果不明の取込を「ない」と断定しない文言（既存）を維持する。

## 追記 2026-11-04（Codex の実ブラウザ確認で見つかった不具合: リセット後も選択が残る）

発見（Codex、localhost の実ブラウザ）: 状態 `on_hold`・口座（bank）・開始日／終了日 2026-10-27 で「絞り込む」→ 1 行（9020）。続けて「リセット」リンク（Next の `Link`、ソフトナビゲーション）を押すと、一覧は全 3 行に戻り日付も消えるが、状態は `on_hold`、口座は bank のまま表示された。

修正（最小）: `page.tsx` の `FilterForm` に `key={ledgerHref(customerId, parsed.filters, 1)}` を付けた。顧客と有効な絞り込みから作る正規の URL（`page` なし）なので、
- リセットや別の絞り込みでは key が変わり、フォームが作り直されて `defaultValue` が新しい値で入る。
- 同じ絞り込みのページ送り（前へ／次へ）では key が変わらず、再マウントしない。
- GET のみ・`page` を送らない・クライアントでの取得や状態の追加なし（`"use client"`・`useState`・`useEffect` は使っていない）。無効入力時も、残す有効な項目から key ができる。

制限（正直に）:
- 同じ絞り込みのまま、ユーザーが未送信で選択を変えた後にページ送りをしても、key は変わらないため、その未送信の選択は残る（意図どおり。送信していない値を一覧に反映しない）。
- ある絞り込みの状態でユーザーが選択だけ変え、同じ URL に戻るリンクを押しても、key が同じなので未送信の選択は戻らない。今回の再現条件（絞り込み済み→リセット）とは別で、今回は直していない。
