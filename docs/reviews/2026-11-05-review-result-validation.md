# 人の確認の記録(record_human_review)の成功結果が UUID かどうか検証されない: 実装前の期待記録

作成: 2026-11-05（コードとテストを書く前の期待の記録。実装後にこの節を書き直さない。期待が誤っていた場合は末尾に日時と理由を追記する）。

## 目的

`submitReview`（`src/lib/review/submit.ts:99-117`）は、RPC `record_human_review` がエラーなしで返した `data` を `z.string().parse(data)`（`submit.ts:116`）で検査するだけで、`{ ok: true, reviewId }` として返している。この RPC の戻り値は `uuid`（`supabase/migrations/20261020000700_record_human_review.sql:81`、`20261105041046_reject_duplicate_hold.sql:16`）なので、空文字や UUID でない文字列は、正常な応答ではあり得ない。

コード読取による現状の予測（Claude は実行していない）:

| RPC 成功時の `data` | 現在 | あるべき扱い |
| --- | --- | --- |
| 正しい UUID 文字列 | 成功 | 成功（変えない） |
| `""`、`"   "`、`"rev-1"`、UUID の前後に文字が付いたもの | 成功（`reviewId` がそのまま画面側へ） | 結果不明の例外 |
| `null`、`undefined`、数値、真偽値、配列、オブジェクト | `ZodError` を投げる（固定文ではない。内部の検査メッセージを含む） | 固定文の例外 |

業務上の問題: `error` が無いのに壊れた応答が来ても「確認を記録した」と扱われ、空の確認 ID が成功として通る。一方、非文字列では固定文でない `ZodError` が上に伝わる。どちらも「結果不明」として一貫して扱うべきである（`docs/development-rules.md` の「再試行・途中失敗の検証」、同じ関数の既存方針 `submit.ts:35-38`）。確認はコミット済みの可能性があるので、`ok:false` ではなく既存の固定文の例外にする。

## 入力と期待する出力（架空データ）

テストは Supabase クライアントの `rpc` をモックする。`decisionId` は `00000000-0000-4000-8000-0000000000aa`、成功時の確認 ID は `00000000-0000-4000-8000-0000000000dd`（架空）。

| RPC の応答 | 期待 |
| --- | --- |
| `{ data: "00000000-0000-4000-8000-0000000000dd", error: null }` | `{ ok: true, reviewId: "00000000-0000-4000-8000-0000000000dd" }`。RPC 引数は従来どおり |
| `data` が `""`、`"   "`、`"rev-1"`、UUID の前後に空白、UUID に文字を足したもの、`null`、`undefined`、`123`、`true`、`[]`、`["<UUID>"]`、`{}`、`{ id: "<UUID>" }` | 既存の固定文の `Error`（`確認の記録結果を取得できませんでした。記録済みの可能性があります`、`submit.ts:73`）を投げる。成功の戻り値は返さない |
| 上の不正な `data` に秘密の目印文字列を含めた場合 | 例外のメッセージ・名前・スタック・原因・独自プロパティのどこにも、返された内容が含まれない |

## 例外・失敗時の扱い
