## 目的

`ReviewBoard`（`src/app/customers/[customerId]/review-board.tsx`）が人の確認（承認・修正・保留・却下・まとめて承認）を送るとき、同じ操作が二重に送られない、かつ「結果不明」のあとに同じ画面から再送できないようにする。

この段階では**テストと期待の記録だけ**を追加する。本番コード・DB・権限・履歴・アクションの意味は変えない。

## 証拠のある不具合

1. **結果不明のあとに即再送できる。** `act` の `catch` は「記録済みの可能性があります。再読み込みして確認してください」と案内するが（`review-board.tsx:130-132`）、直後の `finally` が `busy` を `false` に戻す（`review-board.tsx:133-135`）。保留ボタン・`h` キーは理由があれば再び有効になり、案内を読む前に再送できる。まとめて承認も同じ（`review-board.tsx:158-165`）。
2. **再送すると DB に履歴が増える。** `record_human_review` は `bank_transactions.status` が `proposed` または `on_hold` なら受け付け（`record_human_review.sql:114-117`）、保留は「すでに保留中か」を見ない。応答だけが失われた保留をもう一度送ると、`human_reviews` に保留の行が追加され（`record_human_review.sql:155-159`）、時刻付きの履歴が二重になる。履歴は追記専用なので、あとから消せない。
3. **`useState` の `busy` だけでは足りない。** `act` / `bulkApprove` は `busy` をクロージャで読む（`review-board.tsx:103,141`）。`setBusy(true)` が描画されるまでに届いた古いハンドラ（同じ tick のクリック連打、キー連打、単件→まとめての切替）は `busy === false` のまま通る。

## 期待する設計（実装フェーズ向け）

1. **単一の同期ガード（ref）を、単件（`act`）とまとめて（`bulkApprove`）の両方の入口で共有する。** `useRef` に「送信中」「結果不明」を持たせ、ハンドラの冒頭で**同期的に**確認・設定する。state は表示（無効化・案内）のための写しで、判定には使わない。古いハンドラ・キーイベントも同じ ref を見るので止まる。
2. **送信中は相互排他。** 単件が送信中ならまとめて承認も、まとめてが送信中なら単件も、ボタン・キーのどちらからも送られない。
3. **結果不明（`reviewAction` / `bulkApproveAction` の reject、同期 throw を含む）は、ロックする。** 承認・修正の保存（フォーム送信と Ctrl+Enter）・保留・却下・まとめて承認の**すべて**の書込み入口を、ボタンとキーボードの両方で止める。無効表示も出す。
4. **ロックは再マウント（実際の再読み込み）でだけ解ける。** タブ切替、`items` など props の更新（`router.refresh` 相当）、再描画、明細の切替では解けない。結果不明の案内文もこれらで消えない。
5. **閲覧は止めない。** タブ切替、`j` / `k` での移動、選択、修正フォームを開く操作などの読取・ローカル操作は、送信中もロック中も使える。
6. **既知の拒否（`ok:false`、まとめての `failures`）は結果が確定しているので、ガードを解く。** 利用者が意図して再試行できる。**確定した成功**も解き、結果不明ロックにしない。
7. **ローカルの入力不正（保留の理由が空・空白だけ）はガードを掴まない。** 送信前に判定し、理由を直せばそのまま送れる（`review-board.tsx:106-109` の挙動を維持）。ガードの取得は、この判定のあと、`reviewAction` を呼ぶ直前（同期）に行う。
8. 役割による表示と操作可否は変えない。
