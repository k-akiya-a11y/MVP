# 人の確認の入力に NUL（U+0000）があると、RPC の拒否が「結果不明」になる: 実装前の期待記録

作成: 2026-11-06（コード修正前の期待の記録。実装後にこの節を書き換えない。誤りがあれば末尾に日時と理由を追記する）。この呼び出しで変更するのはこの文書と回帰テストだけで、製品コードは未変更。Claude はコマンド・DB・AI を実行していない。

## 目的

`src/lib/review/submit.ts` の入力スキーマは、`finalEntry.description`（`submit.ts:19`）、`reason`（`submit.ts:22`）、重複解決の `reason`（`submit.ts:125`）を `z.string().max(…)` だけで検証しており、U+0000 を通す。PostgreSQL の text／jsonb は U+0000 を保存できない（公式文書。実 DB では未確認）。そのため `record_human_review` / `resolve_suspected_duplicate` が NUL を理由に拒否すると、`knownRefusal` に一致しない SQL エラーとして `unknownResultError()` が投げられ（`submit.ts:111-113`, `144-146`）、画面は「記録済みの可能性がある」結果不明の状態でロックされる。実際には何も記録されていないのに、担当者が再操作できなくなる。

## 期待する動作（修正後）

1. `submitReview` は、`finalEntry.description`・`reason` に U+0000 が1文字でもあれば、RPC を**呼ばずに** `{ ok: false, error }` を返す（例外は投げない）。`submitDuplicateResolution` も `reason` について同様。位置（先頭・途中・末尾・NUL だけ）は問わず、`action` が何でも（承認・保留・修正・却下）同じ。
2. `error` は固定の日本語文。`NUL` と対象（`摘要` または `理由`）を含み、入力の内容（実際の NUL、`\u0000` の表記、前後の文字列）を含めない。
   - 摘要: `摘要に NUL（U+0000）が含まれているため記録できません`
   - 理由: `理由に NUL（U+0000）が含まれているため記録できません`
3. NUL の除去・置換・切り捨てはしない。拒否だけ。
4. NUL がない入力の意味は変えない: 日本語、改行、タブ、空文字（`description: ""`、`reason: ""`）、`reason: null` は従来どおり検証を通り、値は加工されずに RPC へ渡る。保留で理由が空・空白のみ（全角空白・改行を含む）なら、従来どおり `保留の理由を入力してください` で RPC を呼ばない。
5. 実際の RPC エラー（未知の SQL エラー、SQLSTATE 不一致、通信失敗、不正な成功結果）は、従来どおり固定文の `Error`（結果不明）を投げる。結果不明の判定は弱めない。
