## 本来の期待する振る舞い

`POST /api/customers/[customerId]/statements`（multipart/form-data: file, walletId, formatId）は次の順で判定する。

1. 顧客IDが UUID でなければ 400（認証より前）。
2. 未ログインなら 401。
3. multipart として読めない本文は、内部情報を出さない汎用の日本語 400 JSON。DB には何も書かない。
4. file・walletId・formatId が不正なら 400。
5. 5MB 超は 413。
6. 口座が見えない（存在しない・担当外・RLS で隠れる）なら 404。口座検索の失敗は 500 の汎用文言。
7. 取込は担当者の権限で行い、成功は 200、既知の失敗は 422。

## 調査の証拠（修正前）

実 HTTP・ローカル本番ビルド・実認証・実 RLS での結果。

- HTTP 401 / 404 / 400 / 413 の各ケースで、公開テーブルの件数は変化しなかった。
- 正常な bank / card の CSV は、それぞれ 200 を 1 件ずつ返した。DB には取込 2 件・明細 2 行が登録された。
- 担当者本人からは 2 行が見え、担当外の担当者からは 0 行だった（実認証・実 RLS）。
- **不具合**: 認証済みで multipart の boundary が無い、または本文が途中で切れている場合、応答が **空本文の 500** になった。内部情報の漏えいは無く、DB への書込も無かった。原因は `request.formData()` の拒否が未処理だったこと。

## 修正内容

`src/app/api/customers/[customerId]/statements/route.ts` で `request.formData()` の拒否だけを捕捉し、口座検索・取込の前に `{ "error": "アップロードの形式が不正です" }` を 400 で返す。

- 認証・顧客IDの判定は従来どおり先。401 と顧客ID 400 の優先順位は変えない。
- 413、口座検索エラー、取込の結果（200/422）は変更しない。
- 取込の呼び出しは捕捉しない。例外はそのまま伝え、コミット済みの可能性がある結果を 400 などに誤分類しない。
- 例外の内容は応答にも、ログにも出さない。
- Codex の独立レビューは、この「`formData` の try/catch のみ・取込例外は捕捉しない」という範囲を承認した。
