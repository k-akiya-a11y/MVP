# 取込 RPC の成功結果で、壊れた金額(null・空文字・真偽値)が 0 円・1 円として通る: 実装前の期待記録

作成: 2026-11-05（テストを書く前の期待の記録。実装後にこの節を書き直さない。期待が誤っていた場合は末尾に日時と理由を追記する）。今回の作業はテストとこの記録だけで、製品コードは変更しない。

## 目的

`supabaseStatementImportGateway().importRows`（`src/lib/statements/gateway.ts:26-52`）は、RPC `import_bank_statement` の成功結果を `resultSchema`（`gateway.ts:9-23`）で検証する。件数 `count` は `z.number().int().nonnegative()`（`gateway.ts:5`）で厳格だが、金額 `yen` は `z.coerce.number().int().nonnegative()`（`gateway.ts:7`）で、検証の前に `Number(値)` へ変換される。

Claude は実行していない。コード読取による予測（JavaScript の `Number()` の規則）:

| RPC が返した値 | `Number()` の結果 | 現在の `yen` | あるべき扱い |
| --- | --- | --- | --- |
| `null` | 0 | 0 円として成功 | 失敗 |
| `""`、`"   "` | 0 | 0 円として成功 | 失敗 |
| `false` | 0 | 0 円として成功 | 失敗 |
| `true` | 1 | 1 円として成功 | 失敗 |
| `[]`（空配列） | 0 | 0 円として成功 | 失敗 |

対象は金額 5 項目: `income_total`、`expense_total`、`inserted_amount_total`、`skipped_amount_total`、`suspected_amount_total`。

「元明細と処理結果の件数・金額を照合する」「金額は整数(円)で扱う」（`docs/development-rules.md`、`AGENTS.md` 8 章）に反する。RPC の応答が壊れても、取込は「成功・合計 0 円」の要約として画面に出てしまい、金額の照合（読めた行 = inserted + skipped + suspected）が黙って崩れる。壊れた金融データは、成功として扱わずに失敗(例外)で止める(fail closed)べきである。

## 入力と期待する出力（架空データ）

テストは Supabase クライアントの `rpc` をモックし、実サービスは呼ばない。基準の正常応答は次の 1 行の配列（UUID は架空）。

```
[{ import_id: "00000000-0000-4000-8000-000000000001",
   inserted_count: 2, skipped_duplicate_count: 1, suspected_duplicate_count: 1,
   income_total: 500, expense_total: 100,
   inserted_amount_total: 600, skipped_amount_total: 300, suspected_amount_total: 200 }]
```

### 受け入れる(成功する)金額

| 金額の値 | 期待 |
| --- | --- |
| 整数の number（`0`、`1`、`600`、`Number.MAX_SAFE_INTEGER`） | その数値で成功 |
| 数字だけの文字列（`"0"`、`"600"`、`"9007199254740991"`）。bigint が文字列で返る場合を想定 | 数値へ変換して成功 |
| `0`（number・`"0"`） | 成功。0 円の取込は正当 |

返却値の形(`importId`、`insertedCount`、`skippedDuplicateCount`、`suspectedDuplicateCount`、`incomeTotal`、`expenseTotal`、`insertedAmountTotal`、`skippedAmountTotal`、`suspectedAmountTotal`)と各数値は、現在と同じ。

### 拒否する(例外を投げる)金額 ― 5 項目それぞれで確認

| 区分 | 値 |
| --- | --- |
| 欠損・空 | `null`、`undefined`（項目なし）、`""`、`"   "` |
| 真偽値 | `true`、`false` |
| 負 | `-1`、`"-1"` |
| 小数 | `12.5`、`"12.5"`、`"1.0"` |
| 安全でない整数 | `Number.MAX_SAFE_INTEGER + 1`、`"9007199254740992"`、`"9007199254740993"`（number に変換すると丸められ別の金額になる） |
| 数字以外の文字列 | `"abc"`、`"1e3"`、`"0x10"`、`" 12 "`、`"+5"` |
| その他 | `NaN`、`Infinity`、`[]`、`[7]`、`{}` |

例外が投げられ、成功の要約は返らない。5 項目のうち 1 項目だけが壊れていても全体を失敗にする(一部の項目だけ 0 に置き換えない)。

### 変えない挙動

- RPC がエラーを返す → 従来どおり `明細の登録に失敗しました: <message>` の例外（`gateway.ts:39`）。
- `data` が配列でない、空配列、2 行以上 → 例外（`.length(1)`）。
- `import_id` が UUID でない、件数項目が文字列・負・小数・null → 例外（`count` は元から厳格）。
- RPC への引数（`p_customer_id` ほか 8 項目）は変えない。呼出しは `import_bank_statement` を 1 回だけ。
- `recordFailure` は UUID 文字列だけを成功とし、RPC エラーは `取込の失敗を記録できませんでした: <message>` の例外。

## 例外・失敗時の扱い

- 検証失敗は例外のまま上へ伝える。呼出し元（`import.ts`）で握りつぶさない。この記録では、呼出し元の変更や、例外メッセージの文言の固定はしない（テストは「投げること」を確認する）。
- 数字だけの文字列を許すのは、bigint の列を文字列で返す環境があり得るため。コード中のコメント(`gateway.ts:6`)は number で返ると書いているが、どちらでも壊れないことを確認する。
- 先頭ゼロ(`"007"`)と `"-0"` の扱いは、この記録では固定しない。先頭ゼロの数字文字列は、`history.ts:14-18` の `amount`（`/^\d+$/` → `Number`）と同じ「数字だけの文字列」の表現の契約で受け入れられる（`"007"` は 7）。これは会計方針ではなく既存の表現の契約であり、新しい業務判断は要らない。当初の期待（固定しない・テストで確認しない）は変えず、ここに明確化だけを加える。`"-0"` は数字だけの文字列ではないので拒否される。

### 修正前の実測（Codex の報告による。Claude は実行していない）

Codex が `tests/unit/statement-gateway-result.test.ts` の 189 件を修正前に実行した結果: 61 件失敗・128 件成功、終了コード 1、422ms。`z.coerce` による変換で壊れた金額が通ることが再現した。これは観測した修正前の基準であり、修正後の結果ではない。

### 基準の応答の訂正

「入力と期待する出力」の基準の応答は `inserted_amount_total: 600` と書いたが、`income_total + expense_total = 600` に対し 600 + 300 + 200 = 1100 で整合していなかった。誤りだったので、テストの基準を `inserted_amount_total: 100`（100 + 300 + 200 = 600）に直し、写像の期待も `insertedAmountTotal: 100` にした。項目ごとの型境界のテストは 1 項目だけを差し替えるため合計が合わなくなるが、gateway は金額の照合をしないので、照合とは独立に項目の型だけを確かめる（テスト内にも注記した）。

### コードの修正の説明

`src/lib/statements/gateway.ts:6-11` の `yen` を `z.coerce.number()…` から、`z.union([z.number(), z.string().regex(/^\d+$/)]).transform(Number).pipe(z.number().int().nonnegative().safe())` に変えた。`src/lib/statements/history.ts:14-18` の `amount` と同じ契約である。number か数字だけの文字列だけを `Number` に変換し、変換後は 0 以上の安全な整数だけを受け付ける。null・空文字・真偽値・配列・指数表記・16進・符号つき・前後の空白は変換前に拒否され、`"9007199254740992"` などの丸められる値は `.safe()` で拒否される。「bigint は number で返る」という誤解を招くコメントは、number でも文字列でも返り得るという内容に直した。件数 `count`、`resultSchema` の形、RPC 名・引数、エラー文言、DB・マイグレーション、UI は変えていない。
