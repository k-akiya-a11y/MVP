# 顧客別の明細CSV取込の記録（読取専用）: 実装前の期待記録

作成: 2026-11-04（実装前）。実装後にこの節を書き直さない。期待が誤っていた場合は、末尾に日時と理由を追記する。

## 目的

明細CSVのアップロードで結果が分からなかったとき、画面は「取引の一覧と取込の記録を確認してから、必要な場合だけもう一度取り込んでください」と案内する（`src/lib/statements/upload-result.ts` の `UPLOAD_UNKNOWN_MESSAGE`）。しかし「取込の記録」を見る画面がない。顧客ごとに既存の `statement_imports`（成功・失敗の取込記録）を読むだけの画面 `/customers/[customerId]/imports` を追加し、顧客の承認画面とアップロード欄から辿れるようにする。

## 入力

- URL の顧客ID、任意の `?page=N`（1 始まり。不正・範囲外は 1。確認の履歴と同じ `parseHistoryPage`）。
- ログイン中の担当者の権限（`createUserClient`、RLS）。`service_role` は使わない。
- 読む表は `customers`、`statement_imports`、`wallets`（口座名）、`staff_members`（取込者名）。マイグレーションで確認した列だけを使う（`20261020000300`、`20261021000100`、`20261023000100`）。

具体例（架空）: 顧客「テスト商事」に、
(a) 10-03 14:00 銀行CSV `oct.csv`（口座「普通預金」）: 成功。元の行 5 = 読めた 4（登録 2・読み飛ばし 1・重複の疑い 1）+ 金額0の行 1（5行目「金額が0」）+ 読めない行 0。入金 10,000 円・出金 3,000 円（計 13,000 円）= 登録 8,000 円 + 読み飛ばし 2,000 円 + 疑い 3,000 円。
(b) 10-02 09:00 カードCSV `card.csv`: 7 行目「日付を読めません」で失敗。元の行 20。取込なし。
(c) 10-01 に旧形式の記録（元の行数・ファイル名なし）。

## 予測する出力

- 新しい記録が上（`imported_at` 降順、同時刻は `id` 降順）、1 ページ 50 件。前へ／次へのリンクだけ。検索・絞込・書込操作なし。
- 各件: 取込日時（JST）、ファイル名、口座名と口座ID、取込者名とID（読めなければ「名前を読めません」と ID、記録がなければ「記録なし」）、CSV 形式、状態（成功／失敗）、元の行数（`source_row_count` が null なら「不明」）。
- 成功: 読めた行・登録・読み飛ばし・重複の疑いの各件数、入金・出金・登録・読み飛ばし・疑いの各金額、金額0で取引にしなかった行（行番号と理由）。(a) は「読めた行 4件（入金 10,000円・出金 3,000円）」「登録 2件 8,000円」「読み飛ばし 1件 2,000円」「重複の疑い 1件 3,000円」と、内訳が合計と一致して並ぶ。
- 失敗: 「取り込んでいない」「0件・0円は取込がなかったことを表し、元のファイルに金額がなかったことの証明ではない」「元ファイルの金額合計は計算していない」と明示し、読めなかった行を行番号つきで表示。(b) は 0 円を金額として並べない。
- 照合: 読めた行 = 登録 + 読み飛ばし + 疑い、入金 + 出金 = 内訳の合計、元の行数 = 読めた行 + 金額0の行 + 読めない行が崩れていれば、その取込に警告を出す（成功の画面にしない）。
- 案内文: 取込の記録が見つからないことは、結果不明だった取込が登録されていないことの証明ではない。件数は取込時点の記録で、あとで重複の疑いを解決しても変わらない。この記録は承認でも freee への登録でもない。自動の再取込・再送はしない。
- 大量の金額0行・失敗行は先頭 100 件まで表示し、残りは「ほか N 件は省略」と件数を示す。

## 例外・失敗時の扱い

- 顧客IDが UUID でない、または RLS で顧客が見えない（権限外・存在しない）: 何も読まず 404。
- 読込エラー・応答の形式不正・他の顧客の行や口座の混入・ID の重複・件数や金額が安全な整数でない（文字列・数値とも）: 固定の汎用エラー文のみ。「記録なし」とは別の表示。空の成功にしない。
- 記録 0 件（1 ページ目）: 「取込の記録はまだありません」＋記録なしは未登録の証明ではない旨。2 ページ目以降で 0 件: 範囲外の案内と 1 ページ目へのリンク。
- 口座・取込者が読めない: 取込の行は残し、ID を表示して「名前を読めません」と明示する。
- 金額0行・失敗行の jsonb が想定の形でない: その項目を「形式が不正で表示できません」とし、警告する。補完・推測しない。
- 古い記録の `file_name`・`csv_format`・`imported_by`・`source_row_count` が null: 「記録なし」「不明」のまま表示し、補わない。
- サーバーの 1 回の応答上限で切れても、必要な件数に届くか空応答になるまで読む。表示できる最終ページ（10000）より古い記録は、次へのリンクを作らず「これより古い記録は辿れない」と明示する。

## 判断と理由

- 金額・件数は 0 以上の安全な整数だけを受け付け、文字列の bigint も `Number` に変換後に安全性を再確認する（丸められた値は安全範囲を超えるので拒否される）。範囲外は例外で、ページは汎用エラー文を出す。
- 照合の警告は DB の制約（`statement_imports_reconciled`、`_failed_has_errors`）と同じ内容を読んだ値で確かめ直すもの。制約があるため通常は出ないが、旧データや制約の外の変更で崩れた記録を成功に見せないために出す。警告が出ないことは正しさの証明ではない。
- 失敗の記録は 0 件・0 円を金額として表示せず、取込がなかったことと、元の金額合計は未計算であることを書く。

# 独立レビューへの対応（追記: 2026-11-04）

上の「実装前の期待記録」と「実装後の記録」は書き換えていない。期待記録の「照合が崩れていれば警告を出す（成功の画面にしない）」を、画面が満たしていなかった点をレビューが指摘した。

## 指摘と対応

1. **警告があるのに見出しが「成功」**: 期待（成功の画面にしない）に反していた。警告があるときは見出しを「要確認（記録に不整合）」にし、記録された状態は警告欄の先頭に「記録上の状態: 成功／失敗」として別に残す。警告がなければ従来どおり。テスト: 警告つきの成功・失敗で `<h2>` が成功／失敗にならないこと。
2. **行番号 0**: 現在の解析ではファイル全体の誤りの行番号が 0 なので、「ファイル全体: …」と表示し「0行目」とは書かない。読込側の行番号は 0 以上の安全な整数のみ有効とし、負数は金額0の行・読めなかった行の形式不正（invalid、警告）として扱う。テスト: 行 0 の表示・読込、負数の invalid。
3. **元の行数の意味**: `source_row_count` は解析・マイグレーションの定義どおり見出し行と空行を除く数なので、ラベルを「元のファイルの行数（見出し・空行を除く）」に変えた。
