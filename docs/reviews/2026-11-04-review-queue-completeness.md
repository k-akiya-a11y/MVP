# 承認キュー読込の完全性修正（初期リリース前の正しさ）

対象: `src/lib/review/queue.ts` の `loadReviewQueue`（読み取り専用。DB・RLS・RPC・会計方針・依存関係は変更しない）。

## 実装前の期待記録（2026-11-04、コード・テストを書く前の記載。書き換えない）

### 目的
承認画面のキューが、サーバー側の応答行数の上限（PostgREST の max-rows）や 1 対多の履歴で黙って欠けたり、必須の関連行が無いのに静かに空へ縮んだりしないようにする。

### 現状の問題（コードで確認済み）
- 明細・マスタ・口座・重複の疑いは `fetchAll` だが、`inChunks` は ID を 200 件に分けるだけで、1 チャンクの応答は range なし。
  `latest_ai_decisions` / `past_journal_entries` / `human_reviews` / `staff_members` / 重複元の `bank_transactions` は、上限が 200 未満だと関連行が落ちる。
- 保留（`human_reviews` の hold）は 1 つの判断に複数付くので、既定の 1000 行でも切れ得る。
- 最新判断が無い明細は `continue` で黙って消える。重複元が無い重複の疑いは `flatMap` で `[]` になり、未処理の仕事が隠れる。

### 入力と具体例（架空）
- 顧客 C に proposed/on_hold の明細 t-1..t-N、各 1 件の最新判断、保留が判断ごとに 0〜1500 件。
- サーバーの上限 cap=2、ID 450 件（200 件ごとに 3 チャンク）。

### 予測する出力
- 上限に関わらず、全明細・全判断・全保留・全過去仕訳・全重複元が揃った `ReviewQueue`。
- 保留は `created_at` 昇順、同時刻は `id` 昇順で決定的（ページをまたいでも重複・欠落なし）。
- 判断・過去仕訳・保留・重複元の問い合わせは `customer_id` を明示して絞る（`staff_members` は顧客を持たないので RLS のみ）。
- 顧客が見えない（RLS で null）ときは `null` を返し、二次読込は一切しない。
- `canApprove` は従来どおり `is_admin` の RPC 結果。承認・ロール・状態は変えず、書込みもしない。

### 例外・失敗時の扱い
- 2 ページ目以降のエラー、`data` が null／配列でない: 例外（空キューにしない）。`fetchAll` の既存挙動。
- 全件読込後に必須の最新判断が無い明細、または必須の重複元が無い重複の疑い: 一般的で秘密を含まない固定文言の `ReviewQueueLoadError` を投げる（空キューにしない）。
- 判断が同じ明細に複数返る（view は 1 件のはず）: 同様に失敗。
- 任意の参照（過去仕訳の例）が無い: 従来どおりその例だけ省く。担当者名が読めない（RLS）: 従来どおり「担当者」。
- 真に空（対象明細 0 件）は空キューで正常。

### 変更しない範囲
スキーマ・RLS・RPC・会計方針・依存関係・`fetchAll`・ページ・`record_human_review`・承認ロール。

## 実装メモ（実装後に追記）
（2026-11-04 追記。上の期待は書き換えていない。）

### データの流れ（`src/lib/review/queue.ts`）
- 明細 ID を `inChunks`（200 件ずつ）に分け、各チャンクを `fetchAll` で空ページまで読む。`fetchAll` は次の開始位置を取得済み件数にするので、サーバー上限が range より小さくても漏れない。
- 最新判断: `latest_ai_decisions`（view は `ai_decisions.*`、`customer_id` あり）を `customer_id` で絞り、`bank_transaction_id`→`id` 順。
- 過去仕訳: `customer_id` で絞り `id` 順。保留: `human_reviews` を `customer_id`・`action=hold` で絞り `created_at`→`id` 順。同じ判断の保留は同じチャンクに入るので、判断内の順序は決定的。
- 担当者名: `staff_members` は顧客列が無いので RLS のみ、`user_id` 順。読めない人は従来どおり「担当者」。
- 重複元: `bank_transactions` を `customer_id` で絞り `id` 順（外部キー `(duplicate_of_id, customer_id)` により同一顧客内に必ずある）。
- 必須参照の欠落: 最新判断が無い明細、同一明細に判断が複数、重複元が無い疑い → `ReviewQueueLoadError`（固定文言、ID・応答を含まない）。任意の過去仕訳が無い場合だけ従来どおり省く。

### 判断と影響
- 業務データ・権限・承認ロール・状態遷移は変更なし（読み取りのみ、`canApprove` は従来どおり `is_admin` RPC）。以前は黙って消えていた明細・重複の疑いが、欠落時は画面の読込失敗として見える。これは意図した変化。
- ページ（`src/app/customers/[customerId]/page.tsx`）は変更していない。`error.tsx` は無いので、例外は Next.js の既定のエラー画面（本番ではメッセージを伏せる）に落ちる。専用のエラー表示（`history/page.tsx` のような try/catch）は範囲外として未実施。要否は Ken の判断。
- 既存の `ok()` / `fetchAll` の例外文言には Supabase のエラー文が含まれる（従来どおり）。本修正の新しい失敗は固定文言のみ。

### テストと限界
- `tests/unit/review-queue-completeness.test.ts`: 自前の in-memory fake PostgREST（eq/in/order/range/max-rows 上限、2 ページ目の error/null、rpc）。
- 限界: 実 PostgREST・RLS・view（distinct on）・実際の max-rows 設定は通らない。fake の order は文字列比較で、DB の照合順序・timestamptz の順序とは一致を保証しない。ここでは未実行（実行は Codex の独立確認に委ねる）。lint・型検査も未実施。

### 理由
- 上の「ページは変更していない／専用のエラー表示は範囲外・要否は Ken の判断」は、当初の依頼が「境界がなければ最小限の汎用的な利用者向け読込失敗表示は可」としていたため、同じ範囲内の修正であり Ken の判断は不要と整理し直した。
- ページ（`src/app/customers/[customerId]/page.tsx`）は、読込失敗の体験を完結させる目的だけで変更した。承認・取込・権限・状態遷移・スキーマ・DB は変更していない。

### 変更内容
- `createUserClient` / `loadReviewQueue` を最小の try/catch で囲み、どの失敗でも固定の日本語・読み取り専用のエラーを表示する。文言は「承認待ちがない」ことを意味しないと明示する。例外の中身・ログ・顧客データは出さない。
- 失敗時は `UploadForm` / `ReviewBoard` / `DuplicatesPanel` を描画しない。出すのは一覧へ戻るリンクのみ（顧客名・各画面へのリンクは出さない）。
- 顧客が見えない（`null`）場合の `notFound()` は catch の外に置き、従来どおり 404 を保つ。
- 正常時の表示・既存リンク（履歴・取込記録・明細一覧・過去仕訳・ルール・メモ）・操作コンポーネントは変更なし。

## 利用者向け引き継ぎ（やさしい説明）
- 今回の修正で、サーバーの応答件数の上限が小さくても、承認キューの参照が黙って欠けることはなくなりました。
