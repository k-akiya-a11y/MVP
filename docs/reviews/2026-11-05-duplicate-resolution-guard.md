## 不具合の証拠（現状）

- `resolve()` は `setBusy(true)` するだけで、同期のガードがない。再描画前に届いた古いハンドラや同じ tick の連打は、`busy` がまだ `false` の描画のハンドラなので、そのまま `resolveDuplicateAction` を再度呼べる。
- `finally` が常に `setBusy(false)` する。想定外の例外（通信切断など、判断が記録済みかもしれない）の後でもボタンが再び押せる。
- 「別の取引として扱う」と「重複として除外」は互いを止める仕組みがない（`busy` の反映が遅れる間は別行・反対の判断も送れる）。
- 「重複として除外」は承認者だけのボタンだが、`canApprove` が `false` に変わった後の古いハンドラはそのまま呼べる（DB の関数でも拒否されるが、画面側でも送らない）。

## 目的

重複の疑いの判断を、レビュー画面（`review-board.tsx` の `idle | pending | unknown`）と同じ安全な境界で送る。
1 つのパネルにつき、同期的に確認・更新できるガードを 1 つだけ持つ。

## 入力と具体例（架空データ）

顧客 `11111111-1111-4111-8111-111111111111`。重複の疑い 2 件: `D1`（2026-10-31・1,000 円・「振込 テスト商店A」）と `D2`（2026-10-30・2,000 円・「振込 テスト商店B」）。

| 操作 | 具体例 |
| --- | --- |
| 同じ行の連打 | D1 の「別の取引として扱う」を、再描画前に 2 回呼ぶ |
| 別の行 | D1 の「別の取引」を呼んだ直後に、D2 の「別の取引」の古いハンドラを呼ぶ |
| 反対の判断 | D1 の「別の取引」を呼んだ直後に、D1 または D2 の「重複として除外」の古いハンドラを呼ぶ |
| 結果不明 | `resolveDuplicateAction` が reject / 同期 throw / `undefined` を返す |
| 既知の拒否 | `{ ok: false, error: "この明細はすでに判断済みです" }` |
| 成功 | `{ ok: true, ... }` |
| 担当者 | `canApprove=false`（「別の取引」のみ表示） |

## 予測する出力

- **送信中（pending）**: `resolveDuplicateAction` の呼出しは全体で 1 回。全行の両方のボタンが無効。古いハンドラ（同じ行・別の行・反対の判断）は何も送らない。
- **結果不明（unknown）**: 送信は 1 回のまま。「操作の結果を確認できませんでした…再読み込み…」の案内を出し、全行の両方のボタンが無効のまま。`items` の更新・0 件との往復・再描画・古いハンドラでは解除されない。解除はコンポーネントの再マウント（再読み込み）だけ。
- **既知の拒否（`ok: false`）**: `error` の文をそのまま表示し、ロックを解除する。意図した再試行は 1 回送られる。
- **成功（`ok: true`）**: 案内は消え、ロックを解除して次の操作ができる。
- **担当者**: 「別の取引」は送れる。「重複として除外」は表示されず、`canApprove` が `true` から `false` に変わった後の古いハンドラを呼んでも `resolveDuplicateAction` は呼ばれない。この拒否は、ガードを掴まず、案内もロックも作らない（「別の取引」は続けて送れる）。

## 例外・失敗時の扱い

- 例外の内部文言（`Error` の message やスタック）は画面に出さない。出すのは固定の案内文のみ。
- 結果が `{ ok: true }` / `{ ok: false, error }` のどちらでもない値（`undefined` など）は、結果不明として扱いロックする。
- 判断が記録済みかどうか画面からは分からないので、結果不明の後に「念のため再送」を許さない。
- 実装の方針（計画）: `review-board.tsx` の `WriteGuard` と同じく、`useRef` で同期ガード（`idle|pending|unknown`）を持ち、表示用に `useState` へ反映する。`resolve()` の先頭で `ref` を同期的に確認して `pending` に更新する。`canApprove` は最新の値を `ref` で参照し、古いハンドラでも判定する。`finally` は `unknown` を解除しない（`pending` → `idle` は既知の結果のときだけ）。フック（`useRef`/`useState`）は `items.length === 0` の早期 return より前に置き、0 件を経由してもロックが消えないようにする。

### データの流れ（コード上の位置は変更後のファイル）

1. `guardRef`（`useRef`、`idle | pending | unknown`）が、パネル全体で 1 つの同期ガード。全行・両方の判断で共有する。
2. `resolve()` は、まず `canApproveRef.current` を見て、承認者でないのに「重複として除外」なら何もせず戻る（ガードは掴まず、案内も出さない）。
3. 次に `guardRef.current !== "idle"` なら戻る。`idle` なら、その場で `pending` に書き換える。再描画を待たないので、同じ tick の連打や古いハンドラは 2 回目以降が止まる。
4. `guard`（`useState`）は表示用。`busy = guard !== "idle"` で全ボタンの `disabled` を決める（表示の仕組みは従来どおり）。
5. サーバーアクションの結果は `knownResult()` で判定する。`ok: true`、または `ok: false` かつ `error` が文字列、の場合だけ既知の結果。既知なら `finally` で `idle` に戻し、`ok: false` の文をそのまま表示する。
6. 上記以外（reject、同期 throw、`undefined`、形の崩れた値）は結果不明。固定の案内文だけを表示し、`unknown` のまま残す。例外の中身は画面に出さない。
7. `canApproveRef` は描画のたびに最新の `canApprove` を書き込む。承認者の描画で作られた古い「除外」ハンドラも、最新の権限で判定される。
8. フック（`useRef`/`useState`）はすべて `items.length === 0` の早期 return より前にある。0 件を経由しても `unknown` は消えない。
