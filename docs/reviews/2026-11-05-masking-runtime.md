# 伏字の括弧区切り電話番号の規則が、長い数字で処理を止める: 実装前の期待記録

作成: 2026-11-05（テストを書く前の期待の記録だけ。本番コードは未変更）。実装後にこの節を書き直さない。期待が誤っていた場合は、末尾に日時と理由を追記する。

## 目的

`maskSensitive`（`src/lib/ai/mask.ts`）は、AI に送る自由記述から長い数字を `*` にする（CLAUDE.md 7章）。直前の変更（[括弧・タブ・改行などの区切り](2026-11-05-masking-separators.md)）で加えた括弧区切りの電話番号の規則（`mask.ts:15-17`）は、先頭の数字の長さに上限がない（`数字{2,}` + 開き括弧 …）。開き括弧がない長い数字では、正規表現が「どの数字から始めても、数字の塊の末尾まで読み、開き括弧を探して失敗し、戻って再試行する」ため、処理量が文字数の2乗で増える。

Codex の観測（実際のソースを TypeScript で変換して `node:vm` で実行。Claude は実行していない）:

| 入力（すべて `1`） | 所要時間 |
| --- | --- |
| 1,000 文字 | 約 1 ms |
| 5,000 文字 | 約 6 ms |
| 20,000 文字 | 約 100 ms |

文字数が4倍で時間が約16倍の2乗の増え方である。20万文字なら単純な外挿で数秒〜十数秒（**予測であり、未計測**）。

影響の経路: 明細CSVの取込は5MBまで受け付け、`src/lib/statements/parse.ts` は摘要の長さを制限しない。長い数字だけの摘要を含む明細が仕訳候補づくりに進むと、同期処理の伏字が長く止まり、その間ほかの処理が進まない（可用性の問題。個人情報の漏えいや仕訳の誤りではない）。

この段階では**期待の記録と、失敗するはずの回帰テストの追加だけ**を行う。本番コードは変えない。

## 期待する動作

- **どんな長さの数字でも、伏字は短時間で終わる。** 20万文字の数字でも、1回の呼出しが2秒の上限内に終わる。上限を超えるのは不具合とみなす。
- **伏字の結果は、今の仕様のまま変えない。**
  - 括弧がない長い数字（7桁以上）は、全体を同じ長さの `*` にする（既存のハイフン・連続数字の規則）。
  - 数字の塊のあとに閉じ括弧がない、括弧内が5桁以上、括弧内が空、あとの数字が4桁未満、のような近い形は、括弧規則には当たらない。数字の塊だけを `*` にし、括弧と後ろの文字はそのまま残す。
  - 数字の塊のあとに正しい括弧区切り（`(1234)5678` など、半角・全角）が続けば、続きも含めて全体を同じ長さの `*` にする。
  - 前後の文字（日本語、`10/03 12345`、`TEL(1234)`、`03(12)` など）は変えない。
- **長さの上限や切り詰めを新設しない。** 長い入力を途中で切る、一部だけ伏せる、伏せずに通す、という扱いはしない。出力の長さは入力と同じまま。数字を1文字も残さない（20万桁なら20万個の `*`）。
- 通常の短い文章（`10/03 12345`、`3名 1,234円`、`（株）`、`第(1)(2)条`、`TEL(1234)`、`03(12)`、改行・タブで区切られた短い数字、空文字）は変えない。

## 架空の具体例

`N` = 200,000。数字は半角でも全角でもよい。

| 入力 | 期待する出力 |
| --- | --- |
| `1` × N | `*` × N |
| `摘要` + `1` × N + `終わり` | `摘要` + `*` × N + `終わり` |
| `1` × N + `(1234` + `x` | `*` × N + `(1234x` |
| `1` × N + `(12345)` + `6789` | `*` × N + `(12345)6789` |
| `1` × N + `(1234)` + `567` | `*` × N + `(1234)567` |
| `1` × N + `()` + `5678` | `*` × N + `()5678` |
| `１` × N + `（１２３４）５６７` | `*` × N + `（１２３４）５６７` |
| `1` × N + `(1234)5678` | `*` × (N + 10) |
| `１` × N + `（１２３４）５６７８` | `*` × (N + 10) |
| `電話090(1234)5678まで` | `電話` + `*` × 13 + `まで` |
| `10/03 12345 090(1234)5678` | `10/03 12345 ` + `*` × 13 |

### 理由とデータの流れ

- 原因: 修正前は、数字の塊の各位置（N文字ならN通り）が開始位置の候補になり、そのつど `数字{2,}` が塊の末尾まで読み、開き括弧がなくて失敗して戻る。合計 O(N²)。
- 修正後: 開始位置は塊の先頭だけ。塊の先頭で `数字{2,}` が末尾まで読み、失敗して戻る分は O(N) で、塊ごとに1回。全体は入力長に対して線形。
- 出力が変わらない根拠（括弧規則の一致は塊の先頭から始まるものが必ず先に見つかる）:
  1. 塊の途中から始まる一致があれば、同じ塊の先頭から始めても、続きの部分（括弧以降）が同一で、先頭側の `数字{2,}` はより多くの数字を持つので、必ず一致する。先頭からの一致が存在する以上、走査は先頭で一致し、途中からの一致は採用されない。修正前の走査も同じ先頭で一致していた。
  2. 先頭が1桁の塊は `数字{2,}` を満たさないが、途中から始めても桁数はさらに少ないので一致しない。
  3. 一致の末尾の `数字{4,}` は貪欲で、塊の末尾まで読む。したがって一致の直後の文字は数字ではなく、次の一致の開始位置は常に非数字の後ろにある。直前の一致が塊の一部だけを消費して、残りが新しい「先頭」になる、という場合は起きない。後読みは元の文字列を見るので、一致済みの文字の影響も受けない。
  4. 前の規則（カード番号）が出した `*` は数字ではないので、塊の境界として扱われる。修正前と同じ。
  5. 7桁未満で「そのまま返す」一致も、修正前と同じ位置（塊の先頭）で消費される。
- 全角・半角の数字、全角括弧、長い正しい括弧つきの一続き（例 `1`×N + `(1234)5678` → `*`×(N+10)）は、同じ一致が先頭から作られるので出力は同じ。長さの上限・切り詰め・拒否は設けていない。
- 後読みは幅固定で、Node（V8）が対応している。実行は Node のサーバー側のみ。
