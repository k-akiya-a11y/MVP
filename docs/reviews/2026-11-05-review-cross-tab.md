## 原因（コード上の根拠）

`supabase/migrations/20261020000700_record_human_review.sql`

- 明細を `for update` でロックしたあと、状態が `proposed` または `on_hold` なら受け付ける（`:114-117`）。
- 保留（`p_action = 'hold'`）は「すでに保留中か」を見ない。後から来た保留は、先の保留の確定を待ったあと、ロック後に再評価された状態 `on_hold` を見ても通過する。

## 期待する設計（実装フェーズ向け。最小の変更）

1. `record_human_review` の中で、`bank_transactions` を `for update` で取得したあと（`:114` の直後）、**`p_action = 'hold'` かつ `t.status = 'on_hold'` なら拒否する**。ロック後の状態を見るので、並行する2つ目の保留は先の確定を待ったあとに拒否される。
2. 拒否は例外にする。拒否時は `human_reviews` への INSERT も `bank_transactions` の UPDATE も行われない（ロールバックされる）ので、確認ログも `review_seconds` も増えない。
3. 例外の文言には「すでに保留」を含める（日本語。例: 「この明細はすでに保留中です。管理者の確認を待ってください」）。テストは `/すでに保留/` だけを固定する。文言を変える場合は、テストの正規表現の修正を実装レビューで明示する。
4. 保留 → 承認・修正・却下は従来どおり通す（`t.status = 'on_hold'` でも `p_action <> 'hold'` なら拒否しない）。
5. 権限・閲覧範囲の判定は、新しい判定より前（`:97-112`）のまま。権限のない呼出しは、状態に関する情報を漏らさず従来の拒否（「見つかりません」「管理者だけ」）になる。

### 原因

- 直前の `expect(shape).toEqual(reviewFnBefore)` は**通過**していた。つまり `service_role` の実行権は、マイグレーション適用の**前から**あった（所有者・`proacl`・権限・security definer・`search_path` はすべて前後で同一）。このマイグレーションが権限を広げたのではない。
- 実際の Supabase イメージは、クラスタ／default privileges で `service_role` などに実行権を与える。テスト用の簡易 shim にはそれがない。`svc: false` は shim の環境を前提にした固定値で、テストの誤りだった。
- マイグレーション自身は `revoke all ... from public, anon` と `grant execute ... to authenticated` を明示しており（`20261020000700` と `20261105041046` の両方）、PUBLIC と anon に実行権がないことは適用前のベースラインでも同じ。

### 訂正（テストのみ。製品コード・マイグレーション・DB 権限は変更していない）

- DB の権限を変えてテストを通すことはしていない。
- 前後の厳密な等価比較 `expect(shape).toEqual(reviewFnBefore)` は**そのまま**（弱めていない）。`svc` は固定値ではなく、`expect(shape.svc).toBe(reviewFnBefore.svc)` でベースラインと同じことを求める。
- 固定で求めるのは、環境に依存しない値だけ: `secdef: true`、`anon: false`、`auth: true`、`public_exec: false`、オーバーロード 1 つ、`search_path=`。
