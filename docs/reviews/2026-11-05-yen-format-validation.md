# 金額の書式検査が緩く、壊れた金額を別の金額として取り込む: 実装前の期待記録

作成: 2026-11-05（テストを書く前の期待の記録だけ。本番コードは未変更）。実装後にこの節を書き直さない。期待が誤っていた場合は、末尾に日時と理由を追記する。

## 目的

`parseYen`（`src/lib/statements/values.ts:6-26`）は、明細 CSV の出金・入金・利用金額・残高を整数の円にする。現状は符号や括弧を外したあと、**通貨記号・カンマ・空白を位置に関係なくすべて削除**してから数字だけかを調べる（`values.ts:17`）。そのため、書式として壊れた金額が、別の金額として黙って取り込まれる。

Codex が実際の `parseYen` で再現した結果（Claude は実行していない）:

| 入力 | 現状の結果 | 問題 |
| --- | --- | --- |
| `1,23` | 123 | カンマの位置が不正（3桁区切りでない）のに通る |
| `1,,234` | 1234 | カンマの連続を黙って詰める |
| `1円2` | 12 | 数字の途中の通貨記号を黙って詰める |
| `1 2` | 12 | 数字の途中の空白を黙って詰める |

明細の金額が黙って変わることは、CLAUDE.md・開発ルールの「明細を黙って捨てない」「元明細と処理結果の件数・金額を照合する」に反する。誤った金額は、取込・重複キー（`parse.ts:186-201` の金額と残高）・仕訳候補・人の承認画面まで、そのまま流れる。

この段階では**期待の記録と、失敗するはずの回帰テストの追加だけ**を行う。本番コードは変えない。

## 期待する動作（受け付ける書式）

既存の README・コメント・テストで文書化済みの日本円の整数表記だけを受け付ける。新しい書式は足さない。

1. 前処理: NFKC 正規化（全角数字・全角カンマ `，`・`￥`・全角括弧・全角マイナスなどは半角になる）と、外側の空白の除去。結果が空なら `null`（空欄は金額なし）。
2. 符号（任意・どちらか1つ）:
   - 先頭の `-` `△` `▲` のいずれか1つ。
   - 全体を囲む `(` と `)`。
   - 負の値になる。符号なしは正。
3. 通貨記号（任意）:
   - 数字の前に `¥` または `\`（NFKC 後。`￥` は `¥`）を**高々1つ**。既存の「バックスラッシュを円記号として使う」互換を維持する。
   - 数字の後に `円` を**高々1つ**。
   - 前の記号と後ろの `円` の併用（`¥1,234円`）は、既存の文書化例（`¥ 1,234円`）のとおり有効。
4. 空白: 上の**境界**（符号と記号／数字の間、記号と数字の間、数字と `円` の間、括弧の内側）にだけ許す。
5. 数字の部分:
   - カンマなしの数字列（`1234`）、または
   - 先頭1〜3桁 + 「`,` + ちょうど3桁」の繰り返し（`1,234`、`12,345,678`）。
6. 範囲: 安全な整数（`Number.isSafeInteger`）まで。正負とも。`0` は有効（`0` と、符号付きの 0 は値として 0）。

### 受け付けない書式（誤りにする）

- カンマ位置の誤り: `1,23` `1,2345` `,123` `123,` `1,,234` `12,34,567` `1234,567` `1,234,56`
- 数字の途中の通貨記号: `1円2` `1¥2`。重複・位置違いの記号: `¥¥1,234` `\¥1,234` `1,234円円` `円1,234` `1,234¥` `1,234円¥`
- 数字の内側の空白・タブ・改行（黙って連結しない）: `1 2` `1 234` `1\t2` `1\n2` `1,234 567`
- 既存どおり誤り: 小数 `100.5` `1,234.00`、プラス `+500`、指数 `1e3`、外貨 `$1,234`、文字 `abc`
- 符号の重複・括弧の不整合: `--500` `△-500` `(500` `500)`

誤りの文言は既存の様式を使う: 書式の誤りは `金額を整数の円として読めません: "<入力>"`、範囲外は `金額が大きすぎます: "<入力>"`。例外の型（`Error`）も変えない。

## 取込（`parseStatementCsv` / `importStatementCsv`）での期待

- 出金・入金・カードの符号付き利用金額・**金額が0でない行の残高**のいずれかが誤りなら、その行は `errors` に `{ line, message }` として入る。行番号は CSV 上の行（見出し行を含む1始まり。クオート内の改行があっても行の開始位置）。
- 1行でも `errors` があれば、**ファイル全体で `importRows` を呼ばない**。他の行が有効でも同じ。
- 取り込まなかったファイルは `recordFailure` に、`customerId` `walletId` `fileName` `formatId`、`errors`（理由と行番号）、`sourceRowCount`（見出し行より後の空でない行数 = rows + ignored + errors）を渡す。戻り値は `{ ok: false, errors, failureRecordId }`。
- 有効な書式の金額（`¥ 1,234円`、`△1,500`、`(1,500)`、全角、空欄の残高 = `null`）は、これまでどおり取り込める。
- BOM 付き UTF-8 の架空の CSV と、モックの `StatementImportGateway` で確かめる。

## 文書化されていない曖昧な点（方針を決めない。実装前に Ken とすり合わせる）

次は既存の文書・テストに書かれておらず、このテストでは**値を固定しない**。

- 符号と通貨記号の順序: 現状は `-¥500` `△¥500` `(¥500)` を受け付け、`¥-500` は受け付けない。上の期待は「符号／括弧が外側、記号がその内側」という現状の順序を前提にしたが、`-¥500` を文書化済みとは言えない。
- 符号の直後の空白（`- 500`）と括弧内側の空白（`( 500 )`）: 現状は通る。上の「境界の空白を許す」に従うが、文書化例にはない。
- 先頭ゼロ（`007`、`0,123`）: 現状は 7 と 123 になる。どう扱うかは未定。
- マイナス記号の別字形（`−` U+2212、`ー`）: NFKC では `-` にならず、現状は誤り。
- `-0` の符号: 現状は `-0`（負のゼロ）になりうる。テストは値が 0 であることだけを見る。
- 符号が全角でも NFKC により半角になる前提（`－`）。
- 1行内の千円単位表記・`千円` `万円` などの単位語、全角の `円` 以外の円表記（`圓`）は対象外。誤りになる想定だが、文書化された入力ではない。

### 実装（本番変更は `src/lib/statements/values.ts` の `parseYen` のみ）

- 符号（`-` `△` `▲`）または括弧の除去は従来どおり。その後、通貨記号・カンマ・空白を一括削除する処理をやめ、残りを次の文法で**先に検査**する: `^(?:[¥\\]\s*)?(\d+|\d{1,3}(?:,\d{3})+)(?:\s*円)?$`。
- 先頭の `¥`（NFKC 後の `￥` を含む）か `\` は高々1つ、末尾の `円` は高々1つ。空白は記号と数字、数字と `円`、および符号・括弧の内側の境界だけに許す。
- カンマは「先頭1〜3桁 + `,`3桁の繰り返し」のときだけ外して数値化する。数字の内部の空白・記号・不正なカンマ位置は、連結せず `金額を整数の円として読めません` にする。
- 維持したもの: 空欄は `null`、負のゼロ（`-0`）の挙動、`Number.isSafeInteger` の検査と `金額が大きすぎます`、NFKC、`parseStatementDate`、有効な先頭ゼロ（`007` `0,123`）、0円行の扱い（`parse.ts` は未変更）。プラス・通貨記号が符号より前（`¥-500`）・新書式・桁数制限は足していない。
