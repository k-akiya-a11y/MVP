# 修正フォーム（EntryEditor）: 税区分 0 の扱い: 実装前の期待記録

作成: 2026-11-06（本番コード・テストを変更する前の期待）。実装後にこの節を書き直さない。期待が誤っていた場合は、末尾に日時と理由を追記する。

## 目的

`EntryEditor`（`src/app/customers/[customerId]/review-board.tsx`）で、税区分コード 0（`queue.ts:9` のとおり、マスタにあれば 0 は正当な値。実 freee で 0 が何を指すかは未確認で、以下の「対象外」は合成例のラベルにすぎない。現行の seed では税 2 が対象外で、本作業の税 0 は合成マスタ `SYNTH-TAX-ZERO`）を、「未選択」と区別して扱う。

## 証拠のある不具合（コード上）

`review-board.tsx` の `EntryEditor` は、未選択と 0 を同じ数値 0 で表している。

- `valid = entry.account_item_id > 0 && entry.tax_code > 0`（478 行付近）: 税区分が 0 の案は、正当な値なのに保存ボタンも Ctrl/Cmd+Enter も `onSubmit` も止まる。
- `value={entry.tax_code || null}`（504 行付近）: 0 は `null` になり、プレースホルダー「選択してください」が表示される。0 が選ばれていることが画面から分からない。
- `onChange` の `v ?? 0`: 選択を外すと 0 が入る。0 を正当な値として許すと、「未選択」が 0 として送られる恐れがある（この修正で最も注意する点）。
- 提案がない明細の `emptyEntry()` は `tax_code: 0` で、未選択の初期値と正当な 0 が区別できない。

根拠はコードの読取りと合成テスト（予定）だけで、実ブラウザでの再現は行っていない（未確認）。

## 入力と具体例（架空データ）

税区分マスタ: `{id: 0, name: "対象外"}`、`{id: 21, name: "課対仕入10%"}`。勘定科目マスタ: `{id: 101, name: "通信費"}`。「高」タブの H1 で `e` を押す。

| 状況 | 現状（コードからの予測） | 期待 |
| --- | --- | --- |
| 案が 101／税 0 | 税区分が「選択してください」。保存は無効、Ctrl+Enter は無効 | 税区分は「対象外」が選択済み。保存と Ctrl+Enter は 1 回 `finalEntry.tax_code === 0` で送る |
| 提案なし | 税区分は未選択。保存は無効 | **変更なし**: 未選択（0 を既定にしない）。保存・Ctrl+Enter ともに無効、送信 0 回 |
| 案が 101／税 0 で、税区分を「—」に戻す | 0 に戻る | 未選択（内部は `null`）。保存・Ctrl+Enter・onSubmit が無効、送信 0 回。`null` も 0 も送らない |
| 未選択から「対象外」を選び直す | 保存は無効のまま | 保存可能。`tax_code: 0` を 1 回送る |
| 案が 101／税 21 | 保存可能 | **変更なし**: `tax_code: 21` を 1 回送る |
| 税 0 だが、税区分マスタに 0 がない | 保存は無効 | **変更なし**: 保存・Ctrl+Enter ともに無効、送信 0 回（マスタにない 0 は選べない） |
| 勘定科目が未選択（0） | 保存は無効 | **変更なし**: 税が有効でも無効 |

## 予測する挙動（実装フェーズ向け）

1. 編集中の下書きの型を、`tax_code: number | null` とした `EntryDraft` にする（`EntryJson` 自体は変えない）。`null` = 未選択、`0` = 正当な値。
2. 保存できるかの判定を 1 か所（下書き → `EntryJson | null` の関数）に集める。条件: 勘定科目 `> 0`、税区分が `null` でない、税区分が 0 のときは税区分マスタに 0 がある。通れば `EntryJson`、通らなければ `null`。ボタンの `disabled`、`onSubmit`、Ctrl/Cmd+Enter、親の `onSave` が同じ関数を使う。
3. 税区分セレクトは `entry.tax_code`（`null` なら未選択）をそのまま表示し、選択を外すと `null` にする（`0` に変換しない）。
4. 親の `onSave` は関数が `null` を返したら `act` を呼ばない。`null` や 0 に丸めた値を `reviewAction` に渡さない。
5. 正の税区分は、これまでどおり画面側ではマスタ照合を追加しない（選択肢はマスタ由来。サーバーの `normalize_final_entry` が最終的に照合する）。

## 例外・失敗時の扱い

- 税区分が未選択・マスタに 0 がない・勘定科目が未選択: 送信しない。メッセージは追加しない（既存の無効表示のまま）。
- 送信中・結果不明ロック・`canApprove` が偽・IME 変換中・長押し・処理済みキー: **変更なし**（既存の `busy`、`guard` ref、早期 return）。
- サーバーが 0 を拒否した場合: 既存の `result.error` 表示のまま。

## テスト（`tests/unit/review-board-submission.test.ts` に追加）

既存の最小 hook 実装による実コンポーネントの呼出しを使い、`render({ masters })` で税区分マスタに 0 と 21 を入れる。税区分セレクトを取得する補助を `renderOnce` に足す。確認する内容: 既存の案 0 の表示と保存、提案なしは未選択で無効、クリア時の無効（ボタン・Ctrl+Enter・onSubmit）と選び直し、通常の 21、マスタに 0 がない場合の無効、勘定科目が未選択の場合の無効、送信ガード（送信中の連打）、`canApprove` が偽ではフォームが開かないこと。`reviewAction` に `tax_code: null` が渡らないこと。

**実装前の予測:** 案 0 の表示・保存、未選択からの選び直しのテストは現状のコードで失敗する見込み。提案なし・21・マスタなし・勘定科目なし・ガード系は通る見込み。これは予測で、実行は Codex。

## 追記 2026-11-06: 実装（Claude。テスト未実行）

- `review-board.tsx`: `EntryDraft`（`tax_code: number | null`）と `finalEntryOf(draft, masters)` を追加。`editing` の型、`EntryEditor` の `entry`/`onChange`、`valid`（`finalEntryOf(...) !== null`）、税区分セレクト（`value={entry.tax_code}`、`onChange` は `v` をそのまま）、親の `onSave`（`finalEntryOf` が `null` なら `act` を呼ばない）を変更。`emptyEntry()` は `tax_code: null`。
- 勘定科目の `v ?? 0` と「正の値が必須」は未変更。サーバー側の検査も変更しない。
- 訂正（独立レビュー対応）: 初版は税区分 0 だけを画面側でマスタ照合し、正の値は照合しなかったが、これは既存の製品契約（利用可能なマスタへの所属は全税区分コードに適用）に反する特別扱いだった。`finalEntryOf` は、`null`・安全な整数でない値・負の値・マスタにない値をすべて一貫して `null` にする。0 もマスタにあるときだけ通る。勘定科目の「正の値が必須」は維持。
- テスト: 旧フィクスチャの `masters` が空だったため、案が実際に使う勘定科目 1／税区分 2 だけをマスタに追加（他のフィクスチャは変更していない）。`tests/unit/review-board-submission.test.ts` 末尾の追加は `it` 15 件（初版の 12 は数え違いで、実際は 13 件。レビュー対応でマスタにない正の値 21 / 999 と不正値（負・安全でない整数・小数）の 2 件を追加）。`renderOnce` に `account` / `tax` セレクトの取得を追加。

- 訂正（最終レビュー対応）: 負の税区分は、マスタに含まれていても拒否する（従来の `tax > 0` による負数拒否を保つ）。変更は 0 を許すことだけで、新しい方針ではない。`finalEntryOf` に `tax_code < 0` の拒否を、安全な整数の検査・マスタ所属の検査と並べて追加した。負数の回帰テスト（マスタに -1 があっても拒否）は残す。
- 表記の注意: 本書とテストの「対象外」は合成例のラベルで、実 freee の分類として検証したものではない。実 freee の税 0 が「対象外」を意味するとは主張しない。
