## 実装（2026-11-06）

変更は `src/lib/review/queue.ts` の `int` の定義だけ（使用箇所・スキーマ・DB・ページは変更なし）。

```ts
const int = z
  .union([z.number(), z.string().regex(/^-?[0-9]+$/)])
  .transform(Number)
  .pipe(z.number().refine((n) => Number.isSafeInteger(n)))
  .transform((n) => (n === 0 ? 0 : n));
```

- 入力は「数値」か「`-?[0-9]+` に完全一致する文字列」だけ。無条件の型変換（`z.coerce`）をやめたので、`null`・`""`・空白・真偽値・配列は型の段階で拒否される。`Number()` による変換自体は、型と書式の検査を通った後に残っている（`.transform(Number)`）。除いたのは一律の強制変換だけである。
- `Number.isSafeInteger` で小数・`NaN`・`Infinity`・安全整数の範囲外（数値でも文字列でも）を拒否する。
- 既存の類似の読込・入力処理と同じ慣習に合わせた: `src/lib/rules/candidate-schema.ts` の `parseIntegerText`（`/^-?[0-9]+$/` と `Number.isSafeInteger`）、`src/lib/statements/history.ts` の `sum`（安全整数）。ただし `parseIntegerText` は画面の入力欄用に `trim()` するが、DB の応答では空白を許さないので `trim` は引き継がない。
- 任意 ID の `null` は、従来どおり使用箇所の `.nullable()` が受ける。`tax_code` の 0、負の過去金額は通る。正の ID という規則は作っていない。

### 暫定にしていた書式の決定（技術的な直列化形式として明示）

「判断を保留する点」だった書式は、業務方針ではなく**整数の技術的な直列化形式**として次のとおり決めた。テストで固定する（未文書の挙動を残さない）。

| 文字列 | 結果 | 理由 |
|---|---|---|
| `"12000"`、`"-300"`、`"0"` | 受理 | 10 進の整数 |
| `"007"` | 受理（7） | `-?[0-9]+` に合う。先頭ゼロは数値として読む |
| `"-0"` | 受理（0。`-0` にはしない） | 同上。`-0` が表示や等価比較に出ないよう 0 に正規化 |
| `" 12 "`、`"12 "` | 拒否 | 空白は不可 |
| `"1.0"` | 拒否 | 小数点は不可 |
| `"+5"` | 拒否 | 符号は `-` のみ |
| `"１２"`（全角） | 拒否 | 数字は ASCII の `0-9` のみ |
| `"-"` | 拒否 | 数字が無い |

テストの追加: 拒否側は `invalidInts` に `" 12 "`・`"12 "`・`"1.0"`・`"+5"`・全角・`"-"` を足し、全 17 位置で検査する。受理側は、`"007"` → 7 と `"-0"` → 0（`Object.is` で `-0` でない）を確かめる 1 件を追加した。`tests/unit/review-queue-completeness.test.ts` のみ変更。
