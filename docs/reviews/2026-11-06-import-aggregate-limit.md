# 取込の合計金額が安全な整数を超えると、登録後に応答検証で失敗する: 実装前の期待記録

作成: 2026-11-06（コード修正前の期待の記録。実装後にこの節を書き換えない。誤りがあれば末尾に日時と理由を追記する）。製品コードは未変更。Claude はコマンド・DB・ネットワーク・AI を実行していない。テストの赤の確認は Codex が行う。

## 目的

`src/lib/statements/values.ts:25` の `parseYen` は1行ごとの金額が安全な整数（`Number.MAX_SAFE_INTEGER` = 9007199254740991 以下）かを確かめる。しかし `src/lib/statements/import.ts:98-113` は、行の金額の合計を確かめずに `gateway.importRows` を呼ぶ。一方、取込結果の検証（`src/lib/statements/upload-result.ts:104-120` の `isConsistent`）は、`incomeTotal`・`expenseTotal`・`insertedAmountTotal` などの集計値がすべて安全な整数であることを要求する。

そのため、1行ごとには安全でも、合計が安全な整数を超えるファイルは、DB への登録が成功（コミット）した後に、応答の検証で失敗しうる。利用者には「失敗」または「結果不明」と見えるのに、明細は登録済みになり、金額の照合もできない。これは「明細を黙って捨てない／元明細と処理結果の件数・金額を照合する」（`docs/development-rules.md` 不変条件）に反する。

## 範囲（今回の対象）

- **登録前の拒否だけ。** 取込対象の全行（`parsed.rows`）の金額の絶対値の合計（入金・出金を区別せず足した値）が `Number.MAX_SAFE_INTEGER` を超えるファイルを、`importRows` を呼ぶ前にファイル全体の失敗として拒否する。
- 「合計」は、登録される行（金額 0 の `ignored` 行を除く）の `amount`（すでに絶対値）の総和。入金だけ・出金だけの合計が個別に安全でも、両者の和が安全でなければ拒否する（応答の保存則 `incomeTotal + expenseTotal` が安全な整数であるべきため）。
- ちょうど `Number.MAX_SAFE_INTEGER` は受け付ける。それを超える最初の行が「超えた行」。
- **会計上の新しい上限は作らない。** 基準は JavaScript の安全な整数の範囲（既存の応答検証と同じ基準）だけ。業務上の金額上限・件数上限は導入しない。

## 期待する動作（修正後）

1. 全行の金額の合計が `Number.MAX_SAFE_INTEGER` 以下なら、従来どおり `importRows` を1回呼ぶ。
2. 合計が超える場合は、`importRows` を呼ばない（一部だけの取込もしない）。`recordFailure` を1回だけ呼び、`{ ok: false, failureRecordId, errors }` を返す。
3. `errors` は1件。`line` は、行を先頭から順に足したとき、累計が初めて `Number.MAX_SAFE_INTEGER` を超える行の**物理行番号**（CSV の見出し・空行・金額 0 の行を含む元ファイルでの行。`parsed.rows[i].line`）。文言は日本語の固定文で「合計」を含み、NUL を含まない。
4. `sourceRowCount` は、パーサが数えた `rows + ignored + errors`（超えた行より後の行も含む）。
5. 金額 0 の `ignored` 行は合計に入れない（0 のため結果は変わらないが、物理行番号の数え方がずれないことを確かめる）。
6. **合計は正確な整数で数える。** 実装では、累計を丸めのある `number` の足し算で比べず、`BigInt` など正確な整数演算で数える（上限付近で丸めにより超過を見逃さないため）。この条件は動作テストだけでは完全に確かめられないので、レビューでコードを確認する。
7. 既存のパース失敗（書式・日付・金額・列・NUL・1行の金額が大きすぎる等）は変えない。`parsed.errors` があれば従来どおりその `errors` だけを返し、合計の判定は行わない（合計のエラーを追加で混ぜない）。

### 訂正（上の「目的」「範囲」の根拠の言い直し）

上の記述（範囲の2点目）は「応答の保存則 `incomeTotal + expenseTotal` が安全な整数であるべき」と読めるが、**これは誤り**。`src/lib/statements/upload-result.ts:117-120` は両辺を `BigInt` で比較しており、入金+出金の合計そのものが安全な整数であることは要求しない（要求するのは各項目が安全な整数であること、`:109`）。

入金+出金の合計（全行の絶対値の和）を上限にする正しい根拠は、次の保守的な登録前の保証である: DB は取り込んだ全行を `inserted_amount_total`（または他の1つの区分）に入れうる。その場合、その1項目が全行の合計に等しくなり、ゲートウェイ・UI の安全な整数の検証（`:109`）を通る必要がある。したがって全行の合計を安全な整数以下に制限すれば、どの区分への振り分けでも各項目が安全になる。現在の検証が `Number` で足しているとは主張しない。

### 実装

`src/lib/statements/import.ts`: `parsed.rows.length === 0` の判定の後、`buildDedupeKeys` と `importRows` の前に、`parsed.rows` の `amount`（正の絶対値）を `BigInt` で順に足す。累計が `BigInt(Number.MAX_SAFE_INTEGER)` を初めて超えた行で、固定の日本語文「取込む行の金額の合計が大きすぎます（安全に集計できる範囲を超えています）」、`line: row.line`（物理行番号）、`sourceRowCount` は全行の数で、既存の `fail` を返す（`recordFailure` 1回、`importRows` 未呼出）。

### 影響と限界

- 影響: 合計がちょうど `Number.MAX_SAFE_INTEGER` 以下のファイルは従来どおり。超えるファイルだけが、登録前にファイル全体の失敗になる。パース失敗は先に返るため変わらない。金額 0 の行は `parsed.rows` に入らないので合計に影響しない。
- 限界: 上限は JavaScript の安全な整数だけで、業務上の金額上限ではない。すでに登録済みのデータは調べていない。DB 側の関数・制約は変更していない。実 DB での挙動は未確認。
- テストのモック: 成功応答が不可能な 0 の集計値を返していたため、方向ごとの `BigInt` の合計から作るようにした（受け付ける例のみ）。テストの期待は変えていない。
