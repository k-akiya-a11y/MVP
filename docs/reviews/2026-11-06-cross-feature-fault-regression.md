# 機能横断の障害回帰検証(実行前の期待値)

日付: 2026-11-06
状態: **実行前**。結果はすべて未確定で、Codex が実行するまで不明。
本書の「期待値」セクションは実行後も書き換えない。結果は末尾の「実行結果」に追記のみ行う。

## 目的

レビュー一括承認の途中で RPC 応答が壊れた場合と、古い画面・並行リクエストが重なった場合でも、次の点が保たれることを確認する。

- 1 行につき論理的なレビューは 1 件だけ。
- 拒否(refusal)は重複レビューにならない。
- 結果が不明(unknown)の操作を自動再試行しない。
- 画面の表示が実 DB と食い違ったまま、さらに変更できる状態にならない。

## 証拠の範囲(重要)

- 使うのは既存の合成データのみ。ローカルホスト(localhost)上の既存 Compose と既存の review-error-fixture が、`proposed` 状態の 5 行 `NORMAL`, `STALE`, `BULK-1`, `BULK-2`, `BULK-3` を提供する。
- これは **CSV 取り込みの証拠でも AI の証拠でもない**。CSV 取り込み・AI 提案の正しさはこの検証から主張しない。
- 本番相当の実 DB、実 AI、課金が発生する操作、バックアップ、push、デプロイは行わない。ここでいう「実 DB」は、上記 Compose が立てる合成ローカル DB を指す。

## 実行前の条件

実行前に次を確認し、その値を結果に記録する。満たさない場合は中止し、結果に理由を書く。

1. 新しいスタックで開始する(前回の残り状態を使わない)。
2. 接続先がすべてループバック(localhost / 127.0.0.1 / ::1)であること。
3. ソースのハッシュを取得して記録する。検証用にコピーしたアプリ(`--rpc-fault` 付き)の元ソースとの対応も記録する。
4. 5 行 `NORMAL`, `STALE`, `BULK-1`, `BULK-2`, `BULK-3` が `proposed` で存在し、レビュー履歴が 0 件であること(既存の verify コマンドで確認)。
5. 一時停止中の予算(budget)文書と、既存の全文書は変更・削除しない。

## シナリオ A: 一括承認 5 件での応答障害

構成: 既存の `rpc-result-fault-proxy` の `bad-review-second` モードと、コピーしたアプリの `--rpc-fault` を使う。

操作: 5 行を一括承認する。

### 期待値

| 項目 | 期待 |
| --- | --- |
| 1 件目・2 件目 | DB にコミットされる |
| 2 件目の応答 | 不正な UUID を返す(障害注入) |
| 3〜5 件目 | 送信されない、または DB に未反映。**未着手のまま** |
| UI の結果 | 「結果不明(unknown)」。成功・失敗のどちらにも断定しない |
| UI の状態 | unknown により、以後の変更操作がロックされる |
| 自動再試行 | しない |
| 実 DB(verify コマンド) | レビュー済み 2 件、`proposed` のまま 3 件 |
| 再読み込み後 | 残り 3 件、履歴 2 件が表示される |
| 重複 | 1 行に複数のレビューが付かない |

補足の期待:

- 2 件目は DB 上ではコミット済みだが、UI は応答が不正なため確定できない。UI は DB を根拠に成功と推測しない。
- 確認は UI の表示ではなく、既存 verify コマンドの出力を根拠にする。
- 再読み込みで初めて、DB の実状態(残り 3、履歴 2)に画面が一致することを期待する。

### 反証条件(いずれかなら不合格)

- unknown のあとに変更操作ができる。
- 3〜5 件目のいずれかが DB に反映されている。
- 1 行に 2 件以上のレビューがある。
- 自動で再送が起きた。
- 再読み込み後の件数が残り 3・履歴 2 と異なる。

## シナリオ B: 古い 2 つ目のタブ/対のリクエスト

実行方法は次の順で選ぶ。実際に使った方法を結果に明記する。

1. **古い 2 つ目のタブ**(逐次操作): 1 つ目のタブで処理した後、更新していない 2 つ目のタブから同じ行を操作する。
2. **対のリクエスト**: 既存の `http-fault-proxy` が、実際に対になった同時リクエストを扱えると確認できた場合のみ実施する。サポートされない場合は実施せず、「未実施」と理由を記録する。新しい仕組みを作って補わない。

### 期待値

| 項目 | 期待 |
| --- | --- |
| 論理的なレビュー数 | 1 行につき 1 件 |
| 後から来た古い操作 | 拒否される(stale として) |
| 拒否の扱い | 重複レビューを作らない。拒否は DB に追加の書き込みを残さない |
| 再試行 | unknown に対して自動再試行しない |
| 画面 | 拒否後も DB と矛盾する成功表示を出さない |

### 反証条件

- 同じ行に 2 件目のレビューが作られる。
- 拒否されたはずの操作が履歴に現れる。
- unknown 後に自動再送が発生する。

## 同時性の報告ルール

- 実際に実行した並行度を、そのまま正確に報告する(例: 逐次の 2 タブ、プロキシ経由で対にしたリクエスト、など)。
- **逐次のタブ操作から「同時実行した」とは主張しない。** 同時性の主張は、リクエストが実際に重なったことを示す記録がある場合に限る。
- 同時性が確認できなかった場合は、「同時実行は未検証」と書く。

### 検証結果(Codex 独立ブラウザ+DB 検証、2026-11-06)

#### 環境と前提

- 新規の使い捨て環境で、既存の localhost 向け Compose 設定を使用した。マイグレーションは 17 件。
- 検証用にコピーしたソース 116 ファイルのハッシュが元ソースと一致した。
- 合成データとして、`proposed` の高信頼度 5 行 `NORMAL`, `STALE`, `BULK-1`, `BULK-2`, `BULK-3` を投入した。この fixture は **CSV 取り込みの証拠でも実 AI の証拠でもない**。

#### シナリオ A: 一括承認 5 件での応答障害

- ブラウザで 5 行すべてを選択して一括承認した。RPC プロキシが、2 件目の成功した `record_human_review` の UUID を不正な ID に差し替えた。
- UI は「結果不明」の警告を表示し、選択を解除し、承認・編集・却下を無効化した。
- DB: `NORMAL` と `STALE` は承認済みで、それぞれレビュー 1 件・履歴 1 件。後続 3 件は未着手の `proposed` で、レビュー 0 件。
- 障害注入は 1 回で、上流応答は 200、`upstreamErrors` なし。再読み込み後の残りは 3 件。
- 判定: 期待値どおり。反証条件には該当しない。

#### シナリオ B: 対のリクエスト

- 実際の IAB タブ 2 つで、既存の HTTP プロキシ(3102)経由で同じ `BULK-1` を選択した。`pair-next` が同一 tick で両方を送信した(間隔 0.472ms)。`pairsDispatched` 1、`pairsFailed` 0。
- 両リクエストとも転送は 200 だったが、業務上の成功は一方のみで、もう一方は既知の「すでに承認済み」拒否だった。
- 両タブの UI とも残り 2 件。拒否は後続の有効な操作を凍結しなかった。
- DB: `BULK-1` は承認 1 件・レビュー 1 件・履歴 1 件のみ。重複なし。
- 判定: 期待値どおり。反証条件には該当しない。

#### シナリオ C(追加): 応答バッファ後の切断

- `BULK-2` を承認した。`drop-next` により、上流の完全な 200 `text/x-component` 応答をバッファした後、応答バイトを 1 つも返す前に下流ソケットを破棄した。
- DB では承認 1 件・レビュー 1 件・履歴 1 件を独立に確認した。UI は「結果不明」警告を出し、変更操作を無効化した。再試行は行われていない。
- 再読み込み後、残りは `BULK-3` の 1 件、履歴は 4 件(`syntheticadmin`、変更前後が一致、先頭 2 件は一括マーカー付き)。
